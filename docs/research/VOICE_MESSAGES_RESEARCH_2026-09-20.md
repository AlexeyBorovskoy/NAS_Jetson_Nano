## 1. Задача и ограничения железа

`@бобик` уже понимает текст (Talk и — по спецификации `2026-09-19-telegram-family-bot-design.md` —
Telegram) через safety-gate → LLM Gateway. Голосовое сообщение из Telegram — это файл
**OGG/Opus, обычно 5–30 с**. Цель — понять, каким путём превратить его в текст, чтобы
дальше пустить по уже существующему пути (gate → шлюз → GigaChat/DeepSeek/локальная модель).

Железо (из `CLAUDE.md`, состояние на 2026-09-19–20, самим этим документом не менялось):

| Параметр | Значение | Источник |
|---|---|---|
| Платформа | Jetson Nano 4 ГБ, ARM64 (Cortex-A57 ×4, 1.43 ГГц), хост Ubuntu 18.04 / Python 3.6.9 | `CLAUDE.md` |
| GPU | CUDA 10.2, JetPack 4.6 — **не используется ни одним контейнером** (`GR3D_FREQ 0%`, аудит 30.08) | `CLAUDE.md`, `docs/audit/` |
| Контейнер NAS API (`homecloud_nasa_api`, где живёт `@бобик`) | `mem_limit: 128m`, занято ~52 МБ → свободно ~**76 МБ** | `docker/compose/docker-compose.nas_jetson_nano-api.yml:11`, `CLAUDE.md` |
| Контейнер LLM Gateway (отдельный, для сравнения размера) | `mem_limit: 256m` | `docker/compose/docker-compose.llm-gateway.yml:8` |
| Контейнер downloads (aria2+AriaNg, для сравнения размера) | `mem_limit: 192m` | `docker/compose/docker-compose.downloads.yml:10` |
| ОЗУ устройства целиком | «плотно»: 2.0/3.9 ГБ занято, доступно ~1.6 ГБ; ZRAM 595/1982 МБ | `CLAUDE.md` |

**Вывод №1 (без веба, из самой раскладки compose):** любой вариант, добавляющий модель
распознавания речи **внутрь** контейнера NAS API, обязан уложиться в оставшиеся ~76 МБ —
это меньше, чем «маленький» LLM Gateway (256 МБ) и даже меньше downloads (192 МБ), у
которых задачи заведомо легче STT-модели. Уже на этом шаге видно: **STT — отдельный
контейнер**, не довесок к NAS API. Подробный расчёт — в §3.

## 3. Рекомендация

### Куда встраивать — вывод твёрдый уже без веба

Любая модель STT — **отдельный контейнер**, не часть `homecloud_nasa_api` (128 МБ, свободно
~76 МБ). Это следует из §1: даже минимальная модель (Vosk small 45 МБ на диске, whisper.cpp
tiny 75 МБ) при типичном для таких рантаймов раздутии в памяти (обобщённая оценка из веба —
НЕ проверено для этой версии и для Jetson) с высокой вероятностью не влезет в 76 МБ
свободного места, а тем более — в 128 МБ лимит целиком. Паттерн в проекте уже есть:
LLM Gateway (256 МБ) и downloads/aria2 (192 МБ) — оба вынесены в отдельные контейнеры
именно по этой причине. Новый контейнер `homecloud_voice` (условное имя) с бюджетом
порядка **192–320 МБ** — ожидаемо необходимый шаг, а не выбор.

Отдельно нужна конвертация **OGG/Opus → WAV PCM 16 кГц моно** (Vosk и whisper.cpp оба этого
ждут). Полный `ffmpeg` — тяжёлый пакет; более узкий `opus-tools` (`opusdec`) декодирует
именно Opus в WAV и по описанию легче — но точных цифр по размеру пакета на Alpine ARM64
в вебе не нашлось (**НЕ ПРОВЕРЕНО**, нужно смотреть `apk add` на самом Jetson или в
Kaggle-контейнере с тем же базовым образом).

### Рекомендация с обоснованием

**Первый вариант для замера: whisper.cpp `tiny` (мультиязычная, квантованная) в отдельном
контейнере, локально, без выхода в интернет.** Обоснование:

1. Проектный принцип уже зафиксирован в `docs/plans/TALK_AI_ROADMAP.md` до этого исследования:
   «Piper (TTS) + whisper.cpp/Vosk (STT)» — локальное решение предпочиталось заранее, и это
   совпадает с общим правилом проекта «сомнение и приватность не делегируются дешёвому пути».
2. Голос — более чувствительные данные, чем текст: в отличие от вопросов к GigaChat, которые
   проходят через redaction-шлюз **до** отправки наружу, сырой звук редактировать перед
   отправкой нечем — гейт работает с текстом. Отправка голоса в любое облако (SaluteSpeech,
   Yandex, Cloud.ru whisper) — это новый класс риска, для которого в проекте есть прямой
   прецедент: ADR-0010 по Immich ML потребовал **отдельного принятия риска** именно потому,
   что превью фото уходят из дома для ML. Голосовые сообщения семьи — тот же по духу случай.
3. Обе локальные модели (Vosk small-ru, whisper.cpp tiny) физически умещаются в бюджет
   контейнера, сопоставимый с уже существующими (LLM Gateway 256 МБ) — уровня риска по памяти
   не выше того, что в проекте уже принято.
4. Whisper — мультиязычная модель, официально не специализированная под русский (README
   whisper.cpp говорит только «multilingual unless `.en`», ни слова про качество по языкам) —
   поэтому **качество на русском не факт, а гипотеза**, и именно её проверяет Kaggle-бейк-офф
   в §4, а не это исследование.

**Явный второй вариант, если `tiny` не подтвердится замером:** **Vosk small-ru** — тот же
профиль (локально, Apache 2.0, 45 МБ), но модель специально обучена на русском корпусе
(в отличие от мультиязычного Whisper), и по конструкции ожидаемо даёт вменяемое качество на
русском при меньшем размере — это тоже гипотеза, не факт, и тоже идёт в бейк-офф. Если ни
`tiny`, ни `Vosk small` не проходят по качеству, следующий шаг — `whisper.cpp base`
(квантованный) при готовности заплатить памятью и временем ответа, а не сразу переход в
облако.

**Явно НЕ рекомендуется на этом шаге:** любой облачный вариант (SaluteSpeech, Yandex
SpeechKit, Cloud.ru whisper-large-v3) как основной путь — не потому что они хуже по
качеству (возможно, лучше), а потому что каждый требует осознанного решения владельца
про голос семьи вне дома, отдельного от уже принятого решения про текст. Облако остаётся
явным запасным вариантом, если локальные модели не проходят по скорости/качеству — тогда
это отдельное решение владельца, а не побочный эффект выбора движка.

## 4. Что меряем на Kaggle и что — на Jetson

Разделение по принципу `docs/integrations/kaggle/README.md`: Kaggle — подготовка и
сравнение на **публичных** данных, домой едет артефакт (файл модели + таблица чисел),
а не работающий сервис; числа времени с Kaggle GPU не переносятся в проект как факт
времени на Jetson (разное железо, там ещё и GPU, которого у контейнеров Jetson нет).

### На Kaggle (общедоступные наборы, ничего семейного)

- **Наборы:** `Golos` (Сбер, github.com/sberdevices/golos, открытая лицензия для
  исследований и коммерческого использования, 1240 часов размеченной русской речи —
  ПРОВЕРЕНО, 2026-09-20) — как основной эталон; дополнительно **Common Voice Russian**
  (Mozilla, краудсорсинг, более «бытовая», ближе по характеру к голосовым сообщениям в
  мессенджере, чем дикторская студийная запись) — как второй срез для устойчивости вывода.
  Брать **небольшую тестовую выборку** (не весь корпус — Kaggle-квоты по месту/сессии
  не измерены, см. `docs/integrations/kaggle/README.md` §4).
- **Что сравнивать:** Vosk small-ru vs whisper.cpp `tiny`/`base` (мультиязычные,
  квантованные и нет) — **WER (word error rate)** на русском тестовом срезе, размер модели,
  качественные примеры ошибок (числа, имена, окончания — то, что реально ломается в русском).
- **Чего Kaggle не скажет:** скорость на ARM без GPU. GPU-время на Kaggle не аналог
  CPU-времени на Cortex-A57 — это два разных профиля исполнения, а не «то же самое, но
  быстрее». Если нужна грубая оценка вычислительной сложности — прогонять сравнение
  **в CPU-режиме** Kaggle-ноутбука (без GPU), это ближе по духу к Jetson, но всё ещё
  не то же железо и не заменяет замер на устройстве.
- **Итог с Kaggle:** таблица WER/размер/типичные ошибки + при необходимости готовый
  квантованный файл модели — домой одним артефактом, без сырых записей семьи.

### На Jetson (по «деплой», после того как модель выбрана по качеству)

- **Метрики:** wall-clock на реальном 5–30-секундном голосовом (синтетическое или из
  собственного тестового чата — не хранить чужие/семейные голосовые дольше проверки),
  занятая память контейнера в рантайме (`docker stats`), поведение под лимитом `mem_limit`
  (падает ли OOMKilled — грабля уже известна проекту по другим контейнерам), время
  конвертации OGG/Opus → WAV, суммарная задержка «голосовое пришло → ответ ушёл» в
  сравнении с текущим таймаутом цепочки (`TALK_BOT_LLM_TIMEOUT=150` c у шлюза,
  правило «таймаут вызывающего строго больше таймаута вызываемого» — STT добавляет
  звено, весь бюджет придётся пересчитать, не забыть).
- **Проверка «после выката — не файлы на диске, а новый код работает»** (правило №14
  `CLAUDE.md`) — актуально и здесь: контейнер собирается через `--build`, не через
  `up -d --force-recreate` (та же грабля, что уже стоила времени в проекте).

## 5. Риски и открытые вопросы к владельцу

### Риски (в т.ч. уже известные проектом грабли, применимые к этой задаче)

- 🔴 **Голос — данные, которые нечем редактировать перед отправкой.** Redaction-шлюз
  (11 категорий, включая имена со склонениями) работает с текстом **после** распознавания.
  Любой путь, где распознавание идёт в облаке (а не на устройстве), отправляет наружу
  **сырую** речь семьи раньше, чем сработает хоть какая-то защита. Это качественно другой
  риск, чем уже принятый для текстовых вопросов.
- 🟠 **Память — узкое место, а не деталь.** ОЗУ устройства уже «плотно» (свободно ~1.6 ГБ,
  ZRAM частично занята). Новый контейнер на 192–320 МБ — это не абстракция, а конкретная
  заявка на кусок и без того тесного ресурса; нужно решение владельца о бюджете, как было
  с LLM Gateway/downloads.
- 🟠 **Таймаут-цепочка удлиняется на одно звено.** Уже пойманная грабля 2026-08-24
  («таймаут вызывающей стороны короче таймаута вызываемой») применима впрямую: STT
  добавляется между Telegram и LLM-шлюзом, и весь бюджет времени по цепочке
  `telegram_front → bot_core → STT → gate → шлюз → провайдер` придётся пересчитать заново,
  а не просто дописать ещё один таймаут по аналогии.
- 🟠 **«Код запекается в образ»** (грабля `CLAUDE.md`) — новый контейнер собирается
  `--build`, а не полагается на монтирование правки поверх старого образа.
- 🟡 **Цифры качества/скорости моделей из веба — не для Jetson.** Benchmark whisper.cpp на
  Raspberry Pi 5 (Cortex-A76) взят как единственная найденная точка отсчёта для ARM
  без GPU, но Pi 5 заметно мощнее Jetson Nano (A57) по одноядерной производительности —
  переносить числа как факт для Nano нельзя, только как верхнюю границу ожиданий.
- 🟡 **Cloud.ru FM и Yandex SpeechKit — цены на голос конкретно не подтверждены.**
  Прайс-лист Cloud.ru для аудио-эндпоинта `whisper-large-v3` в вебе не нашёлся;

## 6. EN summary

`@бобик` already understands typed text via a redaction gate → LLM Gateway. This is
**research only** — no code, no deployment. Task: understand how to turn a Telegram voice
message (OGG/Opus, 5–30 s) into text feeding the same pipeline.

Hardware ceiling: the NAS API container (where the bot lives) is capped at 128 MB, ~76 MB
free today (2026-09-19 baseline). That alone rules out adding any STT engine inside that
container — even the smallest candidates (Vosk small-ru, 45 MB on disk; whisper.cpp tiny,
75 MB on disk) plausibly exceed that headroom once runtime memory is counted, by generic
web estimates that are **not verified for this Jetson**. The project already has the
pattern for this: LLM Gateway (256 MB) and the downloads container (192 MB) are separate
containers for the same reason. A dedicated `homecloud_voice`-style container (~192–320 MB)
is the conclusion, not a choice.

Compared, with sourcing and verification status: Vosk small-ru (CONFIRMED 45 MB, Apache 2.0,
Russian-specific, runtime RAM and Jetson speed NOT VERIFIED), whisper.cpp tiny/base/small
(CONFIRMED disk sizes from the official README; RAM and Jetson-specific speed NOT VERIFIED;
Raspberry Pi 5 numbers found are not transferable to the weaker Jetson Nano CPU),
faster-whisper (ARM64 CPU support exists via CTranslate2/OpenBLAS but a ready aarch64 build
path for this project is NOT VERIFIED), SaluteSpeech (CONFIRMED: 100 min/month Freemium for
individuals closed to new signups since 2026-07-15; paid ≈1200 RUB/1000 min), Yandex
SpeechKit (no permanent free tier; pricing found was contradictory across sources — NOT
VERIFIED), Telegram Premium transcription (CONFIRMED unavailable to bots — no such method
or field exists in the official Bot API reference), Cloud.ru Foundation Models'
`openai/whisper-large-v3` (catalog listing CONFIRMED public by the project's own earlier
probe; audio-endpoint pricing NOT VERIFIED).

Recommendation: start the benchmark with **whisper.cpp tiny (multilingual, quantized), fully
local**, in its own container — matching the project's pre-existing preference (recorded in
`TALK_AI_ROADMAP.md` before this research) and avoiding a new privacy risk class: unlike text,
raw voice cannot pass through the redaction gate before leaving home, so any cloud STT option
is a materially different risk than the already-accepted cloud text path (direct parallel to
ADR-0010's explicit risk acceptance for Immich ML). Explicit second option: **Vosk small-ru**,
same footprint, Russian-specific by construction. Both are hypotheses about Russian-language
quality on this specific hardware, not facts — resolved by a Kaggle bake-off (WER on the
public Golos dataset plus Common Voice Russian, size, and qualitative error review; Kaggle GPU
timing is explicitly not carried over as Jetson CPU timing) followed by a real wall-clock and
memory measurement on the Jetson itself before any deploy decision. Cloud engines remain an
explicit fallback, gated on a separate owner risk decision, not a default.

Open questions for the owner: memory budget for a new container on an already-tight device;
whether a cloud fallback is acceptable if local models fail on speed/quality, and which one;
acceptable answer latency; and where this sits in the existing development queue.
