# 32. Ворота качества — ошибки ловятся локально, а не в бою

> 🇷🇺 Обязательное условие проекта с 2026-08-22. Требование владельца: дефект
> должен находиться **до выката**, а не на живой системе с семейными данными.
>
> 🇬🇧 Mandatory since 2026-08-22: defects must be caught **before deployment**,
> not on a live system holding the family's only copy of its data.

---

## 1. Почему именно эти проверки

🇷🇺 Список ворот собран не из моды на линтеры, а из дефектов, которые **уже
доходили до боевой машины этого проекта**. Каждая проверка обязана иметь свою
историю; проверка без истории — балласт, который начнут обходить.

| # | Что случилось | Цена | Ловится ли, и чем |
|---|---|---|---|
| 1 | `subprocess.run(capture_output=True)` — параметр из Python 3.7, а на Jetson **3.6** | упало в бою | ✅ **vermin** `--target=3.6-` |
| 2 | Незакавыченное `TALK_BOT_DISPLAY_NAME=NAS Bot` в `.env`: `source` под `set -euo pipefail` падал с кодом 127 | **16 дней без бэкапов**, systemd рапортовал `success` | ✅ `check_env_syntax.py` |
| 3 | Регулярное выражение искало `error` и находило его внутри `Completed without error` | ложная тревога в семейный чат | ⚠️ **не ловит ни один статический анализатор** → регрессионный тест с настоящим образцом |
| 4 | `sudo -S` вместе с heredoc — пароль записался в файл вместо содержимого | пароль в `/etc`, ротация | ⚠️ статикой не ловится → правило процесса |
| 5 | `$host` вместо `$http_host` в nginx — терялся порт в редиректах | сломанные редиректы | ⚠️ **в репозитории код был верным** — расхождение живого конфига с git → сверка `репозиторий ↔ живая машина` |

🇬🇧 Each gate exists because of a real incident. Note #5: the repository was
already correct — the bug lived only in the hand-edited config on the live VPS.
A linter would never have caught it; only a drift check does.

## 2. 🔴 Обязательные требования

### 2.1. Перед коммитом

**`bash scripts/quality/preflight.sh` обязан пройти.** Хук `.githooks/pre-commit`
запускает его автоматически. Включение на новой машине:

```bash
git config core.hooksPath .githooks
pip install vermin          # главная проверка проекта
```

Обход `--no-verify` допустим только осознанно и **объясняется в сообщении коммита**.

### 2.2. Перед выкатом на живую систему

1. **Ворота пройдены** (см. 2.1).
2. **Выкладывается код вместе с тестами**, а не по отдельности. Раздельные версии
   уже давали ложный зелёный результат в соседнем проекте.
3. **Проверка синтаксиса на самой цели** до установки: `bash -n` / `ast.parse` —
   на целевой машине, её интерпретатором.
4. **Бэкап или откат наготове**: `.bak.YYYYMMDD` рядом либо доказанная команда отката.

### 2.3. После выката — 🔴 самое пропускаемое

**Убедиться, что работает новый код, а не файлы лежат на диске.**

```bash
systemctl show <unit> -p ActiveEnterTimestamp   # когда служба стартовала
stat -c %y <файл>                                # когда файл изменён
```

🇷🇺 Долгоживущий процесс импортирует модули один раз при старте. В соседнем
проекте четыре правки были скопированы, тесты на цели прошли (963/963), работа
объявлена выкаченной — а бот **три часа отвечал старым кодом**. Поймали только
сравнением этих двух отметок времени.

🇬🇧 A long-running process imports its modules once. Copied files plus green tests
do not mean the new code is running. Compare the timestamps.

5. **Проверить поведение на живых данных отдельной командой**, а не по тишине в
   журнале. Тишина неотличима от «не запустилось».

### 2.4. Проверки, которые нельзя делать через `if`

🔴 **Ворота не должны зависеть от семантики shell.**

```bash
if ( set -euo pipefail; . "$f" ); then ...   # ❌ bash отключает errexit в условии
out=$(проверка); rc=$?                        # ✅ код возврата берётся явно
```

Первая версия проверки `.env` в этом проекте была написана первым способом и
**пропустила файл с тем самым дефектом №2**. У соседнего проекта на тех же граблях
упавший линтер рапортовал успех, и код уехал в бой.

## 3. Что проверяют ворота

| # | Проверка | Чем | Блокирует |
|---|---|---|---|
| 1 | Синтаксис bash | `bash -n` | да |
| 2 | ShellCheck | `shellcheck -S error` | да, если установлен |
| 3 | Синтаксис Python | `ast.parse` | да |
| 4 | **Совместимость с Python 3.6** | `vermin --target=3.6-` по `scripts/` | да |
| 5 | **Значения `.env`** | `check_env_syntax.py` | да |
| 6 | Секреты | `check_no_secrets.sh` | да |
| 7 | `docker-compose` | `docker compose config --quiet` | да, если есть docker |
| 8 | **Регрессии семантики** | `tests/unit/test_*.py` | да |

⚠️ **Проверка 4 распространяется только на `scripts/`** — они исполняются на самом
Jetson. Код в `services/` живёт в контейнерах со своим Python (3.9+) и под это
требование не подпадает. Разделение проверено замером, а не предположено.

## 4. Чего статика не ловит — и чем это заменено

🇷🇺 Честный список: инструментов на эти классы дефектов не существует.

| Класс | Замена |
|---|---|
| Семантика («ответ не по вопросу», подстрока внутри слова) | регрессионный тест с **настоящим** образцом из живого вывода |
| Конфликт двух потребителей `stdin` (`sudo -S` + heredoc) | правило процесса: писать файл в `/tmp` от `admin`, затем `sudo cp` |
| Расхождение git ↔ живая машина | сверка конфигов и версий; отдельная задача, см. §6 |
| «Служба молчит» как класс отказа | алерты Фазы E: отсутствие сигнала — тоже сигнал |

## 5. Что сознательно НЕ взято

🇷🇺 Отказ так же важен, как выбор: лишний инструмент — это цена без пойманных дефектов.

| Инструмент | Почему нет |
|---|---|
| **mypy** | С 2025 не умеет таргетить Python 3.6 (требует 3.9+). Для нашей главной задачи бесполезен |
| **bandit** | Сам требует Python 3.10+, ловит другой класс проблем |
| **ruff как замена vermin** | Направление проверки обратное; минимальная цель `py37`, `py36` не поддерживает вовсе. Проверено замером: `capture_output` он **не поймал** |
| **act** (локальный прогон CI) | Требует Docker Desktop и образ от 500 МБ; дешевле запустить сами ворота |
| **systemd-analyze verify** | Требует WSL2 с systemd; юниты просты и меняются редко |
| **QEMU / ARM64-эмуляция** | Рабочий, но тяжёлый путь. `vermin` отвечает на тот же вопрос за секунды. Держать как разовый глубокий тест перед крупными изменениями |
| **bashate, shfmt** | Стиль, а не ошибки; `shellcheck` уже покрывает содержательную часть |

## 7. Главный урок

> 🇷🇺 Все три постмортема соседнего проекта за один день сводятся к одной фразе
> владельца: **«проверка мерила не то место и выглядела убедительно»**. Тесты звали
> функцию напрямую, минуя проводку; сравнение «до/после» сравнивало файл сам с
> собой; упавший линтер рапортовал успех. Зелёный результат — не доказательство,
> пока не известно, что именно он измерял.
>
> 🇬🇧 All three of the neighbouring project's post-mortems reduce to one sentence:
> *the check measured the wrong place and looked convincing.* A green result proves
> nothing until you know what it measured.
