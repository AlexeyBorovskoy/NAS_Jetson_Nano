## 1. Сводка

- **Проект:** домашний NAS на Jetson Nano: три FastAPI-сервиса (NAS API с ботами Talk/Telegram
  и качалкой, LLM-шлюз, STT), сторож на VPS, ~50 shell-скриптов обслуживания, systemd, compose.
- **Стек (ФАКТ, из манифестов):** Python 3.6 на хосте Jetson (скрипты, проверяет `vermin`),
  Python 3.12 в контейнерах (`services/*/Dockerfile`), bash, docker compose, systemd.
  Тесты: pytest (5 наборов) + 21 unit-скрипт, CI — `.github/workflows/quality-checks.yml`.
- **Размер:** 103 продуктовых файла, **10 116 строк кода** (Python 6 287, shell 3 829);
  тестов 7 362 строки (0,73 на строку кода). Топ-10 файлов по размеру — **39,6 %** кода.
- **Пороги:** 7 модулей в `fail`, 27 в `warn`; циклов импорта нет; дублирование в продуктовом
  коде 2,6 % (с тестами — 6,3 %).
- **Тесты:** все зелёные (344 pytest + 21 unit). Покрытие сервисов и скриптов — **68 %**
  (строки и ветки вместе, `raw/coverage.txt`).

**Три главных вывода**

1. **Риск сосредоточен в четырёх файлах NAS API и шлюза**: `talk_bot.py`, `llm-gateway/app/main.py`,
   `telegram_bot.py`, `downloads.py` — 2 469 строк (24 % кода) и **19 из 34** коммитов-исправлений,
   затронувших `services/`. Худший из них — `talk_bot.py`: меняется чаще всех (18 коммитов,
   8 исправлений) и покрыт хуже всех (**47 %**).
2. **Причина разрастания — отсутствие слоя сервисов.** Роутеры FastAPI служат друг другу
   библиотекой: `talk_bot.py` зовёт **9 приватных функций** чужих роутеров, `telegram_bot.py`
   зовёт приватную `_build_health` роутера Talk. Каждая новая возможность бота поэтому
   ложится в `talk_bot.py` (механизм K/C, §4).
3. **Исправления не доходят до копий.** Доказано дважды: фикс зависания HDD (API-1) не
   перенесён в проверку HDD бота — путь к повтору инцидента 2026-09-20 открыт (F-01); фикс
   раскладки хоста (`layout.sh`) не дошёл до 10 скриптов и встроенного сторожа USB (F-09).
