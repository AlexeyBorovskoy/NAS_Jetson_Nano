28,0195 МиБ, heartbeat ≤11 с; 3491 fast / 59 minute / 82 process snapshots;
PID 4991, рестартов 0. Observer завершился успешно: 61 точка за 3600,058 с.
Утром 22.10 процесс тот же, текущий RSS 24,06 МиБ, но VmHWM **43,89 МиБ**

Следующий блок — память/запись; успешный час не закрывает более длительный бюджет.
Ноль записи на SD в обычном режиме отдельно не доказан: `fallback=0` этого не измеряет.

файлов сверяются отдельно. Git HEAD устройства не переключался: прежние правки

Первая живая приёмка нашла квадратичную обработку длинных логов и чрезмерную

Проверки: полный preflight и metrics ratchet прошли без исключений; единственное
предупреждение полного прогона — локально нет ShellCheck. Windows blackbox:
314 passed, 5 skipped. Linux: полный набор blackbox/container-watchdog —

Boot-service включён и успешно завершён. Изолированная synthetic-проверка
SSD→HDD архива, immutable retry и отказа копирования прошла; только затем включён

## Что и зачем меняется

Сборщик сохраняет питание, память, процессы, события контейнеров и журнал;
`nas-why` объясняет имеющиеся признаки с уровнем уверенности. Снимок загрузки
связывает предыдущий heartbeat с новым pstore и журналом. D2 дополняется кратким
разбором; OPS-1 замечает устаревший heartbeat. Это инструменты диагностики,
а не доказательство, что причина каждого сбоя будет определена.

Код: `services/blackbox/`, точки входа и helper в `scripts/monitoring/`, четыре
`systemd/nas_jetson_nano-blackbox*`, тесты `tests/blackbox/`. Установщик копирует
юниты и managed CLI launcher, **не включает и не запускает** службы.

## До установки

1. Проверить `git status --short` и текущий коммит на Jetson. Не делать `git pull`
   поверх ручных правок; переносить только принятый пакет с проверкой diff/хешей.
2. До переноса пакета сохранить commit, локальные diff и прежние
   `nas_jetson_nano-boot-alert.py`, `nas_jetson_nano-container-watchdog.py`,
   `blackbox_alerts.py` (если существует) из `scripts/monitoring/` в закрытый
   `.agent-work/archives/obs1-source-before-<UTC>/`. Зафиксировать отсутствующие
   пути, сохранить ручные правки. Сохранить прежние юниты, список таймеров,
   crontab и агрегат свободного места.
   Не выводить `.env`, реальные ключи, журналы семьи и имена оригиналов.
3. Проверить `/etc/nas-layout.env`, реальное монтирование SSD в `/mnt/storage`,
   группу `adm`, Python 3.6 и systemd 237. Каталоги архива на HDD установщик
   не создаёт; это делает изолированный worker после проверки монтирования.
4. На целевом хосте сверить доступность каналов INA3221 от root. Если датчик
   недоступен, значения остаются неизвестными; это не нулевое напряжение.
5. Пройти полный `bash scripts/quality/preflight.sh`. Linux-проверка обязательна:
   Windows пропускает три sysfs-фикстуры с двоеточием в имени и может пропустить
   тесты symlink. Проверка синтаксиса 3.6 не заменяет проверку на хосте.

Используется штатная раскладка: SSD `/mnt/storage/blackbox`, резерв на SD
`/var/lib/nas-blackbox/fallback`, HDD `/mnt/hdd2tb/backups/blackbox`. Для иных
путей сначала согласовать конфигурацию, `ReadWritePaths` юнитов и корни OPS-1;
не менять один путь изолированно. Запись в каталог под отсутствующим SSD
запрещена. Сырые данные наблюдения наружу и внешним моделям не отправлять.

## Команды установки

При новой установке сначала выполнить проверку пакета и транзакционное применение:

```sh
bash scripts/monitoring/install_blackbox.sh --check
sudo bash scripts/monitoring/install_blackbox.sh --apply
```

Установщик сохраняет прежние файлы в `.agent-work/archives/blackbox-install-*`,
проверяет units и выполняет `daemon-reload`. При ошибке восстанавливает прежние
units и CLI; каталоги и rollback-копии сохраняются. Чужой CLI, symlink или каталог
вместо unit-файла не перезаписывается.

После проверки пакета включить boot и collector. Archive timer включать только
после успешной отдельной synthetic-приёмки архива:

```sh
sudo systemctl enable --now nas_jetson_nano-blackbox-boot.service
sudo systemctl enable --now nas_jetson_nano-blackbox.service
systemctl show nas_jetson_nano-blackbox.service -p ActiveState -p ActiveEnterTimestamp
stat scripts/monitoring/nas_jetson_nano-blackbox.py services/blackbox/blackbox/collector.py
```

Время входа в active должно быть позже изменения исполняемого кода; после обновления
нужен контролируемый restart и проверка ошибок импорта. Один timestamp не доказывает,
какие модули загружены. Первый запуск не восстанавливает отсутствующую историю.
Включение archive timer после synthetic-приёмки:

```sh
sudo systemctl enable --now nas_jetson_nano-blackbox-archive.timer
```

## Контроль результата

- Финальный час 21.10 14:11:59–15:11:59 UTC принят по всем критериям ниже
  (`accepted=true`, observer exit 0). Прогоны с 13:37 и 14:01 прерваны
  и не засчитываются. Ночной срез 22.10 выявил превышение целевого VmHWM
  и существенный объём записи: задача более длительного бюджета остаётся открытой.
- Для полного часа требуются: fast delta больше 3000; не менее 55 minute rows и
  55 distinct process snapshots; средний CPU не выше 5%; `/proc` VmHWM не выше
  40 MiB; cgroup peak не выше 64 MiB; PID и restart count не меняются; свежий
  heartbeat текущего boot не старше 120 секунд. Итог фиксировать, только если
  все условия выполнены на полном часовом интервале.
- Последняя read-only quick check подтвердила целостность трёх БД, запись текущего
  boot и соответствие snapshot его ID. Первый `sudo nas-why --boot -1 --short`
  честно вернул `unknown`: исторических данных предыдущей загрузки не было;
  это не диагноз причины сбоя.
- Snapshot/boot-catalog association дополнительно проверить при следующем
  естественном boot. Не вызывать reboot или потерю питания ради приёмки.
- Synthetic archive acceptance прошла на отдельных тестовых каталогах SSD/HDD:
  проверены manifest/hash, immutable retry и сохранность synthetic source при
  ошибке копирования. Production-архивы этой проверкой не затрагивались.
- Периодическое дочитывание логов ограничено 16 KiB и одним контейнером за итерацию;
  pending batch до 200 контейнеров не сбрасывается. Пропущенный initial backlog и
  oversized records учитываются безопасными маркерами и счётчиками. Сбор старого
  family backlog сам по себе не является целью. Хвост для die/oom/unhealthy —
  отдельный путь: до 200 строк и 1 MiB чтения, до 16 KiB после маскирования.
- Не индуцировать reboot, потерю питания, остановку collector или реальное
  уведомление для этой приёмки; не перезапускать семейные контейнеры. Такие события
  не заявляются проверенными. Сырые логи наружу и во внешние модели не передавались.
- Существующие watchdog hook, HDD guard и SMART сохранены. Резервные копии исходников
  и системных файлов сохранены для отката.

Операции HDD архиватора и runtime `nas-why` изолированы в worker. Родитель ограничивает
ожидание deadline, не блокируется на reaping D-state и сохраняет marker живого worker,
чтобы не плодить процессы. Размер fallback — цель в устойчивом состоянии:
WAL/VACUUM и атомарные замены могут временно требовать дополнительное место. При невозможности удержать
лимит запись событий/минут прекращается; это потеря наблюдений, не успех.

## Откат

```sh
sudo systemctl disable --now nas_jetson_nano-blackbox-archive.timer
sudo systemctl disable --now nas_jetson_nano-blackbox.service
sudo systemctl disable --now nas_jetson_nano-blackbox-boot.service
```

При живом D-worker не удалять его маркер и не повторять запуск. Проверять только
PID и время старта через proc; не пытаться лечить диск размонтированием или
перезапуском держателей. Для восстановления исходных unit/CLI использовать
конкретную резервную копию установки; восстановить только сохранённые файлы,
а новые убрать только по её манифестам `absent`/`cli-absent`, затем
`sudo systemctl daemon-reload`. Вернуть прежние boot-alert/watchdog/helper
из сохранённого до переноса пакета каталога `obs1-source-before-<UTC>`; новый
helper убрать только если его отсутствие зафиксировано. Наблюдения, исходные журналы, архивы, volumes,
монтирования, VPN и оригиналы фотографий не удалять.
