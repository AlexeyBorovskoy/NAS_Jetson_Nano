## Проект

**NAS_Jetson_Nano** — приватный семейный облачный сервер на NVIDIA Jetson Nano 4 GB + USB SSD 250 ГБ + USB HDD 2 ТБ.
Заменяет Google Photos (→ Immich), Google Drive (→ Nextcloud), облачный NAS (→ Samba).

**⚠️ Грабли, проверенные на практике:**
- **OCS API Nextcloud принимает форму, а не JSON.** `_ocs_post` слал `json=` и получал
  `404 / statuscode 998 "Invalid query"`. Из-за этого Talk-бот **не отвечал никому с
  момента запуска Фазы A** — в статусе копилось `processed`, а `replied` оставался 0,
  и ошибка глушилась в `except`. Отправлять `data={...}`. Тот же дефект вероятен
  у других вызывающих сторон `_ocs_post` — не проверено.
- **Код запекается в образ** (`COPY app /app/app`). Правка файла на хосте + `up -d
  --force-recreate` не даёт ничего — контейнер поднимется со старым кодом. Нужен `--build`.
- **Не передавать два base64-файла одной ssh-командой** — склейка через разделитель
  бьёт содержимое, контейнер потом падает с `Attribute "app" not found`. По одному файлу.
- **Картинки принимает только `GigaChat-2-Max`.** Базовая `GigaChat` отвечает
  `422 Model does not support image` — причём файл до этого успешно загружается,
  поэтому ошибка всплывает поздно и выглядит непонятно.
- **GigaChat API не редактирует фотографии** — только смотрит и генерирует новое по
  описанию. Реставрация и ретушь через него невозможны, см.
  `docs/plans/PHOTO_PROCESSING_FEASIBILITY.md`.
- **Фильтр имён — список слов, а не модель.** Уменьшительные (Оля, Ваня, Аня) — другая
  основа и автоматически не выводятся; перечислять все формы. Короткие основы однажды
  молча отбрасывались — теперь видно в `names_dropped` у `/health`.
- В `config/.env` **любое значение с пробелом обязано быть в кавычках** — иначе `source` под `set -e` молча роняет бэкапы, preflight, ssd-recovery и health-чек, а systemd при этом рапортует `success`. Проверять свежестью файлов в `/mnt/storage/backups/database-dumps/`, а не статусом юнита.
- `echo "$P" | sudo -S <cmd>` **нельзя** сочетать с heredoc/stdin — `sudo -S` забирает stdin, и в файл уходит пароль. Писать файл в `/tmp` от `admin`, затем `sudo cp`.
- После правки `/etc/fstab` обязателен `systemctl daemon-reload`, иначе systemd примонтирует по старому сгенерированному юниту.
- FUSE + Docker: если хостовый mount `/mnt/hdd2tb` пересоздан, контейнеры держат мёртвую ссылку → нужен `docker compose up -d --force-recreate`.
- После временных замеров (`python3 -m http.server`) **гасить процесс** — иначе остаётся открытый порт на всю LAN (найден и закрыт при аудите 2026-08-10).
- **`172.29.172.1` — не универсальный адрес VPS, а «тот, кто окажется по этому адресу в текущей сети».** С рабочей станции это наш VPS (`OpenSSH_9.6p1`), с Vostro — **посторонняя машина** (`OpenSSH_8.9p1`): там поднят `awg0`, но маршрутов через него нет, и запрос уходит в чужой шлюз. Проверять принадлежность **баннером**, а не пингом; с Vostro использовать только публичный `95.163.176.103`.
- **`ffmpeg` съедает stdin** и вместе с ним остаток скрипта, переданного через `ssh "bash -s"` — дальше сыплется `команда не найдена` на ровном месте. Ставить `-nostdin` или `</dev/null`. Родня `sudo -S` + heredoc.
- 🔴 **`DOCKER-USER` на VPS пуст — контейнер с `-p 0.0.0.0` обойдёт ufw целиком.** Проверено 2026-08-13: `iptables -S DOCKER-USER` содержит только `-N DOCKER-USER`, ноль правил. Docker вставляет свои правила в `FORWARD` **до** цепочек ufw, поэтому ufw для опубликованных портов контейнеров не работает вовсе. Сейчас не стреляет: наружу опубликован только 443 (Amnezia). Но любой будущий `-p 0.0.0.0:PORT` окажется в интернете молча, вопреки `ufw status`. Находка соседнего проекта, подтверждена самостоятельно.
- **Порты VPS — общий ресурс с другим проектом владельца.** `10022` уже держит туннель Jetson. Прежде чем занимать порт на VPS — сверяться с `ss -tlnp` и с `HOST_CONTRACT.md` на Vostro.
- 🔴 **`.claude/settings*.json` накапливают НАСТОЯЩИЕ секреты.** В allowlist разрешённых команд попадают целые строки из истории вместе со значениями. Найдено инвентаризацией 2026-08-12: в копии проекта `NASA` лежит токен GitHub (`settings.local.json:167`, плюс копия в worktree), в соседнем проекте — sudo-пароль от Vostro открытым текстом. Файлы под `.gitignore`, наружу не уезжают, но при передаче машины, бэкапе профиля или отправке настроек кому-то — помнить.
- 🔴 **Отрицательный результат не называет причину — он называет только себя.** 2026-08-13 `ping` и `ssh` на Vostro молчали, и я построил на этом теорию про исключение `192.168.0.0/16` в split tunneling Amnezia, успев порекомендовать соседнему проекту менять настройку. Настоящая причина: адрес Vostro сменился при переустановке 11.08 (`192.168.75.177` → **`.153`**), и поправка **лежала в моём же локальном документе** — я не открыл его прежде, чем объяснять тишину. По правильному адресу: 0 % потерь, 0–1 мс, `ssh` пускает. Исключение `/16` ни при чём и, судя по маршруту, наоборот **сохраняет видимость корпоративной сети при поднятом VPN** (`192.168.75.0/24` идёт on-link через Ethernet). Признак ошибки: объяснение появилось раньше, чем была проверена входная величина.
- 🟠 **Общий `HOST_CONTRACT.md` нельзя восстанавливать из своей односторонней копии.** 2026-08-12 накат моей копии ужал файл с 673 строк до 180 и стёр весь раздел соседнего проекта; хуже потери то, что в моей версии висел устаревший открытый вопрос, который сосед принял бы за текущее состояние. Правило: **источник истины — только файл на ноутбуке**, свой раздел дописывать, а не перезаписывать файл; локальный `docs/local/VOSTRO_HOST_CONTRACT.md` — черновик. Страховка (принята у соседей): перед перезаписью сравнивать число разделов и останавливаться при уменьшении.
- **`config/certs/russian_trusted_bundle.pem` — сертификат, а не утечка.** Он закоммичен намеренно (нужен для TLS до GigaChat). Автоматические сканеры секретов регулярно принимают его за приватный ключ, потому что смотрят на `-----BEGIN` не разбирая тип. Секрет — только `BEGIN ... PRIVATE KEY`; здесь `BEGIN CERTIFICATE`, и он публичен по назначению.
- 🔴 **Смена IP ломает не один файл, а список файлов.** После 09.08 старый адрес VPS остался в `overwritehost`, `overwrite.cli.url`, `trusted_proxies` Nextcloud и в `/etc/nasa-monitor/nasa-monitor.env` — из-за первого **Nextcloud 13 дней отправлял каждого клиента, включая телефон в двух метрах от NAS, на `https://193.8.215.130:8443`**. Правильный вывод не «поправить адрес», а **перестать навязывать адрес**: снять `overwritehost`/`overwriteprotocol`, и каждый клиент останется там, откуда пришёл. Схема переживает следующую смену IP без правок.
- **Публичный IP VPS недостижим из-под собственного VPN** — он исключён из туннеля по определению, иначе VPN зациклится. Рабочий внешний адрес для клиента под VPN — **`172.29.172.1`**, а не `95.163.176.103`. Проверено замером с рабочей станции: публичные адреса — таймаут, внутренний — HTTP 200.
- **`$host` в nginx отбрасывает порт, `$http_host` — сохраняет.** На нестандартном порту (8080/8443) это молча ломает любой сгенерированный редирект: клиент уезжает на `:80`.

Лечится добавлением имени в `trusted_domains` (вернулся штатный `304`). Nextcloud отвечает на недоверенный домен кодом **`400` и HTML-страницей на 22 КБ**; клиент, ждущий JSON, видит «Bad Request», а настоящая причина — в теле: `{"error": "Trusted domain error.", "code": 15}`. **Меняя `overwritehost`, сразу перечисляй все имена, которыми к Nextcloud обращаются изнутри.**
- 🔴 **Симптом, замеренный внутри собственного окна правок, нельзя объяснять историей.** 2026-08-22 я увидел 400-е и нагрузку 5.9, объявил это застарелым дефектом «бот 12 дней бил в стену» и записал в документацию и в два коммита. ## Экономия токенов: какую модель на что тратить

> Принята 2026-08-13. Источник — `Cost-Aware Model Routing Policy`.
> Оптимизируется **не цена одного вызова, а полная стоимость решённой задачи**.

### Правило выбора

| Модель | Для чего |
|---|---|
| **Haiku** | механика: Glob/Grep, чтение логов и выгрузок, сбор фактов, прогон тестов, форматирование, массовые однотипные операции, подготовка контекста для другой модели |
| **Sonnet** | основная инженерная работа: реализация, рефакторинг, тесты, обычный debugging, code review, анализ архитектуры |
| **Opus** | только при объективной причине: решение затрагивает несколько подсистем, конкурирующие подходы, сложный root-cause, Sonnet уже пробовал и не смог, security review |
| **Fable** | крупные автономные исследования, выходящие за обычный цикл |

Эскалация `Haiku → Sonnet → Opus` **только по причине** (не хватило контекста,
не прошла проверка, задача оказалась сложнее оценки), а не по умолчанию.

### Основная сессия — supervisor

Декомпозировать → выбрать минимально достаточную модель на подзадачу →
делегировать → собрать → проверить противоречия → эскалировать **только
проблемную часть**. Не отдавать всю задачу Opus, если Opus нужен для её десятой доли.

### Что реально экономит здесь

Проверено на практике 2026-08-12:

- **Не тянуть сырьё в контекст.** Скрипт должен считать и вернуть ответ, а не дамп,
  который потом разбирается. Худший случай: читал 254 строки чужого `settings.json`,
  чтобы узнать наличие одного блока — хватило бы `grep`.
- **Объёмное чтение — в Haiku-subagent.** Обратно приходит сводка, а не весь вывод.
- **Батчить проверки** в один вызов вместо трёх.
- 🔴 **Дороже всего обходится повторная работа, а не дорогая модель.** `E:` вместо `E:\`
  стоило полного пересбора скана; кириллица в `.ps1` под cp1251 — трёх заходов;
  `ssh`, съевший stdin, — двух прогонов. Приоритет «минимизация повторной работы»
  стоит **выше** экономии.

### Порядок приоритетов при конфликте

```
1. корректность  2. безопасность  3. воспроизводимость
4. минимизация повторной работы   5. экономия   6. скорость
```

⚠️ **Экономия — пятая, не первая.** Самое ценное в аудите 2026-08-12 родилось из
сомнения в собственных числах (4 → 19 → 14 значений в git) и из вопроса «а точно ли
диск просканирован». Дешёвая модель выдала бы те же неверные числа, просто дешевле.
Механику — вниз, сомнение — оставлять здесь.

### Отчётность

Не докладывать о выборе модели на каждом шаге. При существенной эскалации — одна
строка с причиной. Решилось дёшево — молча продолжать.

## Субагенты

> Принято 2026-08-22 по требованию владельца.

### 🔴 Язык — русский. Всегда и у всех

**Все агенты проекта, включая субагентов, общаются по-русски.** Это относится к
отчётам, заголовкам, пояснениям и к тексту, который уходит владельцу.

⚠️ **Субагент этого правила не наследует.** Он стартует с холодным контекстом, и
если в промпте не сказано — ответит по-английски. Поэтому **первой строкой промпта
субагента писать явно:**

```
ВАЖНО: отвечай ТОЛЬКО НА РУССКОМ ЯЗЫКЕ. Весь отчёт, заголовки и пояснения — по-русски.
```

Проверено на практике: два субагента 2026-08-22 вернули отчёты по-английски именно
потому, что указания не было.

### Как ставить задачу субагенту

- **Требовать разделения фактов и суждения.** Отдельный раздел «оценка» в конце.
  Иначе догадка приезжает с той же интонацией, что и замер.
- **Явно разрешать отрицательный ответ.** «Если не переносится — скажи прямо,
  отрицательный ответ ценнее уклончивого». Работает: оценка по Kaggle вернулась
  честным «нет» с обоснованием, а не вежливым «может быть».
- **Требовать пути и номера строк** для каждого факта — иначе проверить нечем.
- **Запрещать печать секретов**: называть файл и строку, значение — никогда.
- **Чужие проекты — только чтение.** Для этого брать агента `Explore`: у него
  физически нет `Write`/`Edit`, и это надёжнее просьбы «ничего не меняй».
- Возвращать **сводку, а не дамп**: субагент существует, чтобы объёмное чтение не
  попало в основной контекст.

### Когда не звать субагента

Если задача решается двумя `grep` — делать самому. Субагент стартует вхолодную и
заново выводит контекст, который у основной сессии уже есть; на мелочи это дороже.

## Жёсткие правила

1. **НЕ коммитить** реальные `.env`, пароли, токены, ключи, персональные данные.
2. **НЕ трогать** Amnezia VPN контейнеры на VPS — уронит ~25 VPN клиентов.
3. **НЕ удалять** сетевой профиль LAN на Jetson (на устройстве он называется `nasa-lan`, eth0, 192.168.0.50/24).
4. **НЕ открывать** сервисы напрямую в интернет без отдельного решения. Наружу на VPS допустимы только 22, 443 и 40568/udp.
5. **Destructive команды** (rm -rf, форматирование, DROP DATABASE) — только с явного подтверждения.
6. Перед push: `./scripts/security/check_no_secrets.sh`
7. **НЕ форматировать** `/mnt/hdd2tb` — на нём 1.4 ТБ семейного архива, NTFS оставлен намеренно.
8. Любое значение с пробелом в `config/.env` — **обязательно в кавычках** (см. «Грабли»).
9. Любое сетевое оборудование сначала подключать изолированно к workstation: не вводить в production LAN с активным DHCP и не делать factory reset без явного подтверждения.
10. Deco E4 вводится **в режиме Router** и обязан быть переведён на `192.168.0.1/24` (`More → Advanced → LAN IP`) **до** подключения Jetson. Подсеть `192.168.0.0/24` и адрес `.50` не менять никогда (правило №3).
11. **Не выводить EC220-G5 и не сбрасывать его** до успешной приёмки новой сети — это единственный путь отката.
12. Перед заменой роутера **записать тип WAN-подключения и WAN MAC** со старого роутера. Без них новую сеть не поднять, а старого роутера под рукой уже не будет.
13. **Любая работа сохраняет работоспособность VPN на VPS и не затрагивает конечных пользователей** (владелец, 2026-08-22). Проверять до и после: `amnezia-*` не перезапускались, наружу слушают только 22/443/40568, число пиров не уменьшилось. nginx менять через `nginx -s reload`, не пересозданием контейнера.

## Workflow (стандартная процедура)

1. Изменения в файлах проекта (Windows)
2. `git add` + `git commit`
3. `git push`
4. При необходимости применить на Jetson: `ssh admin@192.168.0.50 "cd ~/nasa && git pull --ff-only"` (из дома) или через VPS-jump (см. «Частые операции») — **сначала проверить, не затрёт ли ручные правки на устройстве**
5. Перед запуском Nextcloud/Immich/backup: `sudo bash scripts/storage/storage_preflight.sh`
6. Перезапуск затронутых контейнеров (если compose-файлы изменились и preflight прошёл)
7. После крупных изменений: `git tag` + `gh release create`
8. Обновить README и CHANGELOG

### Обмен по запросу (с 2026-08-13)

У сообщения есть **вид**. Доска перестала быть только односторонней рассылкой фактов:

| Вид | Что означает | Когда перестаёт всплывать |
|---|---|---|
| `fact` | «вот что я проверил». Ответа не требует | после `resolve` |
| `ask` | **запрос данных у соседа** | только когда лёг `answer` |
| `answer` | ответ на конкретный `ask` | сразу; **закрывает свой `ask` сам** |

```bash
python E:\agent_coordination\coord.py post --from nas --to work --subject "..." --body "..."
python E:\agent_coordination\coord.py post --from nas --to work --kind ask --subject "..." --body "..."
python E:\agent_coordination\coord.py post --from nas --to work --kind answer --re m0029 --subject "..."
python E:\agent_coordination\coord.py list --agent nas --open
python E:\agent_coordination\coord.py show m0029          # целиком, не разбирая inbox.jsonl
```

**Правила обмена по запросу:**

1. **`ask` — просьба, а не команда.** Что и в каком объёме отдавать — решает получатель.
   Отказ законен: `resolve` и строка почему. Автономия сессий не меняется.
2. **Спрашивать то, чего у себя нет.** Сосед — источник фактов о своей половине общих
   ресурсов, а не бесплатные руки. Что можно проверить самому — проверять самому.
3. **В запросе называть, что засчитается ответом.** Часто у соседа есть не то, что
   попросили, а эквивалент. И явно разрешать отрицательный ответ: «разницы не видно» —
   тоже данные.
4. **Отвечать своим состоянием, а не догадками о чужом.** Нет доступа проверить —
   так и писать: «принимаю как ваше свидетельство, независимо не проверено».
   Галочка без проверки хуже честного пробела.
5. **Чужое утверждение остаётся чужим, пока не проверено.** Своё — с доказательством
   (чем и когда замерено).
6. **Секретов в запросах и ответах нет** — как и в фактах. Папка вне git, но это
   не хранилище секретов.
