# CPP-1, шаг 1: где Jetson тратит ресурсы — замер 2026-10-12

[English](CPP1_BOTTLENECKS_2026-10-12.md) · [План по целям владельца](../plans/DEVELOPMENT_PLAN_2026-10_OWNER_GOALS.ru.md) ·
[Постановка CPP-1](../../WORK_PLAN.ru.md#запланированный-эксперимент-c--cpp-1)

Вопрос владельца: есть ли в проекте узкие места, ради которых стоит переписывать код на C++.
Шаг 1 плана CPP-1 — измерить CPU, память и задержки на самом Jetson, отделив вычисления от ожидания
диска, сети и внешних API, и, если вычислительного узкого места нет, записать это без переноса кода.

**Ответ: вычислительного узкого места в нашем коде нет.** Весь наш Python занимает 1,7 % одного ядра,
ответы API — единицы миллисекунд. Ресурсы уходят на обвязку: `dockerd`, Nextcloud под опросом Talk и
сам мониторинг. Ни одну из этих статей C++ не уменьшит.

## Как мерили

- 12.10.2026, около 13:00 UTC, окно 300 с, живой Jetson через туннель VPS. Аптайм 17 ч, обычный будний
  день, никто из семьи в это время не загружал фото и не спрашивал бота.
- Только чтение, без sudo и без нагрузки: `/proc/stat`, `/proc/<pid>/stat` и `status`, учёт CPU по
  cgroup (`cpuacct.usage` контейнеров и юнитов), `/proc/diskstats`, `systemctl show`, локальный `curl`
  (20–30 запросов на адрес), хронометраж «что сломалось?» внутри контейнера API (5 прогонов).
- Зонд: [`scripts/quality/cpp1_probe.py`](../../scripts/quality/cpp1_probe.py). Повтор:
  `ssh jetson-via-vps "WINDOW=300 python3 -" < scripts/quality/cpp1_probe.py > out.json`.
  Сырые данные — вне git (`.agent-work/tmp/cpp1/`): в них командные строки процессов.

## Откуда треть ядра у `dockerd` и Nextcloud

Проверено, но причинность не доказана: для этого нужен опыт «до/после» в окне обслуживания.

- **Проверки здоровья.** У 13 из 16 контейнеров они есть: у 9 — раз в 30 с, у 3 — раз в минуту, у
  микросервисов Immich — по умолчанию. Это ≈ 22 запуска процесса в контейнерах в минуту, каждый через
  `runc`. Вероятная причина нагрузки `dockerd` и `containerd`.
- **Опрос Talk.** За те же 5 минут Nextcloud обслужил 73 запроса: 60 — опрос чата Talk ботом фазы A,
  15 — `status.php` (проверка здоровья и Uptime Kuma). Talk семья не использует (заготовка владельца,
  11.10), а опрос продолжается.
- **Мониторинг** сам стоит пятую часть ядра (netdata).

## Вывод

1. **Переписывать наш код на C++ ради скорости незачем.** Наш Python — 1,7 % ядра, ответы — миллисекунды,
   «что сломалось?» ждёт Docker, а не считает. По плану CPP-1 это отрицательный результат, и он
   записывается без переноса кода.
2. **Ресурсы можно вернуть без C++** — тремя правками, каждая с замером «до/после»: реже проверки
   здоровья, остановить или сделать редким опрос Talk, увеличить интервал сбора netdata. Кандидаты в
   REL-5 и ARCH-1.
3. **Главный ограничитель Jetson — память, а не процессор:** доступно 1,4 ГБ, в подкачке полгигабайта.
   Самый крупный наш процесс (речь, 176 МБ) уже нативный внутри; выиграть можно только загрузкой модели
   по требованию, а не переписыванием.

## Чего этот замер не покрывает

- Тихие 5 минут: нет загрузок фото, вопросов боту, закачек, голосовых. Пики — индексация и ML Immich,
  загрузка с телефонов, `pg_dump`, поток Samba — измерит нагрузочное испытание REL-5.
- Одна выборка, без повторов в другое время суток.
- Ответы моделей (секунды) не мерились: это ожидание внешних API и сети, а не вычисления на Jetson.
