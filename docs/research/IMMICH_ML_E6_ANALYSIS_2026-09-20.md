# Immich ML — разведка E6: Cloud.ru vs станция vs «не делать» / Immich ML — E6 spike: Cloud.ru vs workstation vs "don't"

> 🇷🇺 Дата: 2026-09-20. Статус: **разведка с замерами и рекомендацией**, не реализация.
> Ничего не создано в Cloud.ru, на Jetson и на станции; код не написан. Факты о внешнем
> мире помечены `ПРОВЕРЕНО` (источник + дата обращения) или `НЕ ПРОВЕРЕНО` (нашлось из
> вторых рук или не нашлось вовсе — сказано прямо, а не обойдено). Числа не с нашего

## 1. Задача и уже принятые решения владельца

Задача **E6** плана `docs/plans/DEVELOPMENT_PLAN_2026-09_SBER_ERA.md` (строка 228): умный
поиск по смыслу и распознавание лиц в Immich требуют `immich-machine-learning` — сервиса,
который Jetson Nano (4 ГБ, CUDA 10.2, JetPack 4.6) не тянет и на котором его решено не
разворачивать (`ADR-0010`, план «Immich ML на Jetson — не делаем»).

Уже решено владельцем (не переспрашивается в этом документе):

- **D4 (2026-09-19):** Immich ML — в Cloud.ru, **но только если укладывается в бесплатный
  лимит**; риск передачи превью фото наружу принят **именно при этом условии**. Не влезает
  в free tier → нужен другой вариант с числами (эта задача).
- Альтернатива из плана: прогон ML батчем на рабочей станции (ROG, RTX) через обратный
  туннель на `172.17.0.1` — станция за Deco, Jetson её напрямую не достаёт.
- **E6 идёт после E5** (алерт расходов Cloud.ru) — в очереди `docs/plans/DEVELOPMENT_PLAN_2026-09_SBER_ERA.md`
  E5 ещё не выкачен; это не блокирует саму разведку, но блокирует боевой запуск.
- Класс приватности семейных фото — по умолчанию `LOCAL_ONLY` (план, §правило принятия
  решений); отклонение от него требует явного риск-нота, что и делает ADR-0010 для Cloud.ru.

## 2. Что делает Immich ML и что именно уходит наружу

| Факт | Статус | Источник |
|---|---|---|
| Умный поиск по смыслу = CLIP-эмбеддинг (модель `ViT-B-32`, по умолчанию) | ПРОВЕРЕНО | docs.immich.app (веб-поиск 2026-09-20) |
| Распознавание лиц = детекция + ArcFace-модель семейства `buffalo_*` (`buffalo_l` и т.п., InsightFace/ONNX) | ПРОВЕРЕНО | huggingface.co/immich-app/buffalo_l (2026-09-20) |
| **Финальная кластеризация лиц** (объединение эмбеддингов в «человека») выполняется **на самом сервере Immich**, а не на ML-сервисе — удалённый ML отвечает только за детекцию + эмбеддинг | ПРОВЕРЕНО | docs.immich.app/guides/remote-machine-learning |
| На удалённый ML-сервис отправляется **«image preview»** — уменьшенная версия, а не оригинал в полном разрешении | ПРОВЕРЕНО (факт отправки preview, а не оригинала) / **НЕ ПРОВЕРЕНО** точное разрешение/формат в текущей документации | docs.immich.app/guides/remote-machine-learning |
| У ML-сервиса **нет вообще никакой аутентификации** — «as an internal service, the machine learning container has no security measures whatsoever» | ПРОВЕРЕНО, дословная цитата официального гайда | docs.immich.app/guides/remote-machine-learning |
| `IMMICH_MACHINE_LEARNING_URL` (переменная окружения) — **устарела** (deprecated); актуальный способ — раздел «Machine Learning Settings» в админке Immich (URL добавляется через UI, можно несколько URL с фолбэком) | ПРОВЕРЕНО | docs.immich.app/install/environment-variables, github.com/immich-app/immich discussions #6630, #14739 |
| В UI Immich **нет штатного поля «заголовки/headers»** для ML-URL — только сам URL. Базовая HTTP-аутентификация теоретически возможна через `https://user:pass@host` в самом URL (community-приём), но совместимость с HTTP-клиентом Immich для ML **не проверена в этом заходе** | НЕ ПРОВЕРЕНО | gist «Remote Immich ML access with basic auth» (косвенное community-решение, 2026-09-20) |
| Если ML недоступен — сервер Immich **продолжает работать**: загрузка фото, просмотр, альбомы, Nextcloud-независимые функции не блокируются; страдают только задачи, зависящие от ML (умный поиск, лица) — они падают/встают в очередь на повтор | ПРОВЕРЕНО (по совокупности issue-трекера: «uploads can proceed even when the machine learning server is unavailable») | github.com/immich-app/immich issues #28289, #26150 (2026-09-20) |

**Что уходит наружу при варианте «облако» (Cloud.ru или станция через интернет):**
уменьшенные превью фото (не оригиналы) — для CLIP-эмбеддинга и для детекции/эмбеддинга лиц.
Это ровно тот риск, который ADR-0010 требует принять явно, и ровно то, что D4 разрешил
**только при условии** укладывания в бесплатный лимит.

## 3. Оценка нагрузки для наших 7 тыс. фото (с допущениями)

Наши данные (`CLAUDE.md`, замер 2026-08, Immich v2.7.5): **7098 ассетов** = 6686 фото +
412 видео, весь каталог 8.9 ГБ, upload-директория 5.8 ГБ.

**Все числа ниже — оценка по общедоступным сведениям о смежном железе, НЕ замер на
Cloud.ru или на нашей станции.** Правило проекта — не выдавать чужое железо за наше.

| Допущение | Значение | Статус |
|---|---|---|
| ML работает только на CPU (в бесплатном тарифе Cloud.ru Container Apps GPU не упоминается) | CPU-only | ПРОВЕРЕНО косвенно (free tier описывает только vCPU/ГБ ОЗУ) |
| Время CLIP + детекция/эмбеддинг лица на одно фото, современный x86 CPU, 1 поток | ориентир **0.3–1.5 с/фото** (общий диапазон по публичным бенчмаркам CLIP ViT-B/32 и ArcFace на CPU) | НЕ ПРОВЕРЕНО для конкретного класса vCPU Cloud.ru |
| Видео (412 шт.) обрабатывается по извлечённому кадру, не покадрово | сопоставимо с одним фото за клип | НЕ ПРОВЕРЕНО для нашей сборки |
| ОЗУ контейнера ML | Immich: минимум системы 6 ГБ / рекомендовано 8 ГБ **целиком**; отдельно у ML-воркера зафиксирован скачок **до ~7 ГБ во время распознавания лиц** на «взрослых» библиотеках (issue #22717) | ПРОВЕРЕНО как факт скачка; не наш конкретный пик — НЕ ПРОВЕРЕНО |

**Вычислительная часть (чистое CPU-время), первичная индексация 7098 ассетов:**
7098 × 0.3–1.5 с ≈ **0.6–3.0 vCPU-часа** одним потоком. Это заведомо укладывается в
25 vCPU·ч бесплатного лимита Container Apps (Services) сам по себе.

**Критическая оговорка — модель тарификации, а не CPU-время.** У serverless-контейнеров
(и у Cloud.ru, судя по формулировке «vCPU × час использования») обычно тарифицируется
**время, пока выделенный vCPU/ОЗУ закреплены за работающим контейнером**, а не только
занятое процессором время. Если Jetson шлёт превью по одному, с паузами (генерация
превью на самом Jetson, сетевые паузы, темп очереди заданий Immich), контейнер может
провисеть «тёплым» **часы**, а не минуты чистого счёта — тогда именно **ГБ·часы ОЗУ**, а
не vCPU·часы, становятся узким местом: при разумном для нашей маленькой библиотеки
размере контейнера **2–4 ГБ** бесплатных **50 ГБ·ч** хватает на **12.5–25 часов** времени
жизни контейнера в месяц, а не на весь месяц открытым. **Это не измерено — статус
НЕ ПРОВЕРЕНО**, именно поэтому единственный надёжный способ узнать реальную цифру —
тестовый прогон одного альбома с открытым биллинг-консолью Cloud.ru (тот же совет уже
был записан в `docs/plans/IMMICH_ML_CLOUDRU_COST_ESTIMATE.md` §7 и в ADR-0010 «Start with
one album test, not full library»).

**Установившийся режим (только новые фото):** при типичном для семьи темпе (десятки
фото в неделю с телефонов) вычислительная нагрузка пренебрежимо мала (секунды-минуты
CPU в неделю); риск того же типа — простой контейнера «висит тёплым» дольше, чем
реально считает.

**Важно: Container Jobs (5 vCPU·ч / 10 ГБ·ч) — это отдельный от Container Services
(25 vCPU·ч / 50 ГБ·ч) бесплатный пул** (ПРОВЕРЕНО, cloud.ru/docs/evolution/overview/topics/free-tier__container-apps,
2026-09-20). Внешний сторож D3 (задача E5/D3) уже спланирован на Container **Jobs**;
Immich ML как долгоживущий HTTP-сервис ложится на Container **Services** — эти две
задачи не делят один и тот же лимит, конкуренции за квоту между ними нет.

## 4. Вариант А — Cloud.ru Container Apps

### Бесплатный лимит — подтверждён официальной документацией

| Пул | Бесплатно в месяц | Источник |
|---|---|---|
| Container **Services** (нужен для Immich ML — постоянно доступный HTTP-эндпоинт) | **25 vCPU·ч + 50 ГБ·ч ОЗУ** | ПРОВЕРЕНО, cloud.ru/docs/evolution/overview/topics/free-tier__container-apps (2026-09-20) |
| Container **Jobs** (для сравнения — это пул D3/сторожа, не Immich ML) | 5 vCPU·ч + 10 ГБ·ч ОЗУ | ПРОВЕРЕНО, тот же источник |

Это ровно та формулировка, которая уже записана (без подтверждения) в
`DEVELOPMENT_PLAN_2026-09_SBER_ERA.md` строка 311 как «free tier — NOT VERIFIED, проверить
в консоли» — этим документом она **переводится в ПРОВЕРЕНО** по официальной странице
Cloud.ru; численно совпадает с уже записанным ориентиром.

Точная цена **сверх** бесплатного лимита (₽ за vCPU·ч и ГБ·ч) в открытой документации
Cloud.ru при этом заходе **не нашлась** (страница `.../pricing` ссылается на тарифный PDF,
не отдаёт числа напрямую) — **НЕ ПРОВЕРЕНО**, нужен калькулятор в консоли или тарифный
документ `cdn.cloud.ru/docs/legal/tariffs/evolution/current-version/container-apps.pdf`
перед боевым запуском.

### Влезает ли в лимит

По оценке §3 — **вероятно да для вычислительной части (0.6–3.0 vCPU·ч из 25), под вопросом
для ГБ·часов** из-за неизвестной модели тарификации (uptime контейнера против занятости
CPU). Однозначного «да» дать нельзя без тестового прогона одного альбома — это
рекомендация, а не отказ от варианта.

### Холодный старт (упомянут прямо в плане E6: «холодный старт поиска»)

Умный поиск по тексту («покажи фото с тортом») — это **не только фоновая индексация**:
каждый текстовый запрос семьи тоже идёт на ML-сервис (кодирование текста той же CLIP-моделью)
**синхронно**, в момент поиска. Если Container Apps масштабируется до нуля между запросами
(что и даёт экономию — «холодные экземпляры удаляются при прекращении запросов, останавливая
биллинг», ПРОВЕРЕНО по cloud.ru/docs/container-apps-evolution/ug/topics/pricing), первый
поиск после паузы получит задержку **старта контейнера + загрузки ONNX-моделей в память**.
Точное время холодного старта именно на Cloud.ru **в документации не нашлось** —
**НЕ ПРОВЕРЕНО**; по аналогии с сопоставимыми serverless-платформами для Python/ONNX-сервисов
с моделями такого размера порядок величины — от нескольких секунд до нескольких десятков
секунд (общее свойство класса, не измерение Cloud.ru). Практическое следствие для семьи:
первый поиск за сессию может выглядеть «зависшим», последующие в течение некоторого времени —
быстрыми, пока контейнер не остынет снова.

### Как закрыть эндпоинт

| Способ | Реально ли у Cloud.ru Container Apps | Совместимо ли с Immich |
|---|---|---|
| IP-allowlist на уровне сервиса | В найденной документации явного поля «allowlist по IP» для Container Apps **не обнаружено** — НЕ ПРОВЕРЕНО | — |
| Встроенная «Авторизация» Cloud.ru (вход через IAM-аккаунт организации/проекта) | ПРОВЕРЕНО как опция контейнера (cloud.ru/docs/container-apps-evolution) | **Нет** — это интерактивная/IAM-авторизация вызывающего пользователя, а не токен, который Immich умеет подставлять в свой HTTP-клиент к ML-URL; включение этой опции, скорее всего, просто сломает вызовы от Immich (401) |
| Приватная сеть / VPC, недоступная из интернета | Не найдено штатного способа подключить физическое устройство (Jetson) к приватной сети Cloud.ru без отдельного VPN/шлюза внутри Cloud.ru — НЕ ПРОВЕРЕНО, и это плохо сочетается с «бесплатный serverless», а не VM | — |
| HTTP basic-auth, зашитый в URL (`https://user:pass@host`) | Со стороны Cloud.ru это просто HTTP — сервер видит заголовок `Authorization`, если его сформирует клиент | НЕ ПРОВЕРЕНО, поддерживает ли HTTP-клиент Immich ML такую форму URL — нужен тест перед боевым запуском |
| «Публичный адрес без авторизации» + секретный, непубликуемый URL (безопасность через неизвестность пути/порта) | Реально, но слабо: угадывающий сканер портов/URL получит доступ бесплатно к чужому ML-эндпоинту и может как минимум жечь наш лимит | Совместимо технически, слабая защита |

**Вывод по защите:** штатного «включил — и только Jetson может достучаться» механизма,
совместимого с тем, как Immich общается с удалённым ML, **не нашлось**. Реалистичный
минимум — секретный (не публикуемый нигде) URL плюс попытка basic-auth в самом URL,
проверенная тестом на одном альбоме **до** переноса туда боевой библиотеки. Это слабее,
чем «эндпоинт закрыт для мира», и должно быть явно проговорено с владельцем как остаточный
риск сверх уже принятого риска ADR-0010 (там принят риск «превью уходят наружу», но не
явно — риск «чужой человек может тоже дёргать наш ML-эндпоинт, если найдёт URL»).

## 5. Вариант Б — станция батчем через обратный туннель

**Что нужно:**

1. Docker на станции (ROG) сейчас **не поднимается** — гипервизор Windows выключен
   (`HypervisorPresent=False`), нужны права администратора и перезагрузка (`dism`,
   `bcdedit /set hypervisorlaunchtype auto`). Владелец отложил на 13.09
   (`CLAUDE.md`, состояние на 2026-09-12) — **этот документ не проверял, снят ли блокер
   позже**; статус на дату написания — последний известный, требует подтверждения
   владельца перед запуском варианта Б.
2. Подготовка частично сделана заранее (по `CLAUDE.md`): образ под текущую версию Immich,
   переменные окружения вне git, порт ML забинден на `127.0.0.1` (не в LAN).
3. Связь — **не по LAN** (станция за Deco, Jetson за EC220/Deco её не достаёт напрямую) —
   обратный туннель `ssh -R` на `172.17.0.1` (уже рабочая схема для локальной LLM-модели,
   `CLAUDE.md`: «Jetson дотягивается до модели на станции обратным туннелем — проверено,
   0.637 с»). Тот же приём годится для `IMMICH_MACHINE_LEARNING_URL`/Machine Learning
   Settings — технически идентичная задача (проброс с домашней станции на Jetson), но
   **сам факт для конкретно Immich ML отдельно не проверялся** — НЕ ПРОВЕРЕНО, нужен свой тест.
4. Не забыть про уже пойманные в проекте грабли с `ssh -R`: `GatewayPorts clientspecified`
   + явная привязка к `172.17.0.1` (иначе не видно из контейнеров); `ClientAliveInterval 60`
   на принимающей стороне (иначе мёртвая сессия держит порт занятым ~2 часа после
   выключения станции) — оба уже записаны в «Грабли» `CLAUDE.md`.

**Поведение при выключенной станции:** по §2 (issue-трекер Immich) — сервер Immich
продолжает работать без ML-задач: загрузка, просмотр, альбомы не блокируются. Проваливаются
только задачи умного поиска/лиц, которые встают в очередь и (по документированному
поведению Immich) переигрываются при следующей доступности ML-сервера. Семья не теряет
доступ к фото, теряет только смысловой поиск и группировку по лицам, пока станция выключена
— то есть в будни вечером/по расписанию, а не 24/7.

**Плюс варианта Б:** превью не покидают дом вообще (туннель — внутри домашней сети/VPN
контура через SSH, не публичный интернет), это полностью снимает риск §2, который
ADR-0010 явно требует принимать для варианта А.

**Минус:** зависит от станции, которая по факту не работает уже несколько недель для этой
цели (гипервизор), и от присутствия/готовности владельца включать её на прогон.

## 6. Вариант В — не делать ML вовсе

Что теряет семья, честно:

- **Умный поиск по смыслу** («торт», «море», «Уля на площадке») — без ML доступен только
  поиск по имени файла/дате/альбому/geo-тегам (штатные функции Immich не через
  `machine-learning`). Для библиотеки в 6686+ фото за несколько лет это ощутимая потеря
  удобства для тех, кто ищет конкретный момент, а не листает вручную.
- **Автоматическая группировка лиц** («все фото Ульяны») — недоступна; вручную создавать
  и наполнять альбомы по человеку остаётся возможным, просто без автоматизации.
- **OCR/детекция объектов** через ML — недоступны там, где на них опирается смысловой поиск.
- Что **не** теряется: сама библиотека, загрузка, резервные копии, просмотр, шаринг,
  видео — всё это не зависит от `machine-learning` (§2).

Вариант В — самый дешёвый и самый приватный (превью вообще никуда не уходят), цена —
удобство поиска для семьи, а не сохранность данных.

## 7. Рекомендация

**Рекомендация: начинать с Варианта Б (станция батчем), Вариант А (Cloud.ru) держать как
условный запасной путь только после явного теста одного альбома с открытой биллинг-консолью
Cloud.ru — не как основной путь по умолчанию.**

Обоснование:

1. **Вариант Б полностью закрывает риск §2** (превью не покидают дом), ради которого
   ADR-0010 требует отдельного принятия риска — вариант А по определению не может дать
   того же уровня приватности, сколько бы ни укладывался в free tier.
2. **Числа Варианта А не сходятся до конца.** Вычислительная часть (0.6–3.0 vCPU·ч из 25)
   почти наверняка укладывается; ГБ-часовая часть (до 50 ГБ·ч) зависит от модели
   тарификации Cloud.ru (uptime контейнера vs занятость CPU), которая **не подтверждена
   в документации** — это ровно то условие, которое D4 поставил владелец («если
   укладывается»), и по нему честный ответ сегодня — «вероятно, но не доказано».
3. **Защита эндпоинта у Варианта А слабее, чем кажется на первый взгляд.** У Immich ML
   нет своей авторизации, а совместимого штатного способа закрыть Cloud.ru-эндпоинт именно
   под клиента Immich не нашлось — остаётся секретный URL, что хуже полноценного контроля
   доступа.
4. **Вариант Б технически уже почти готов** (туннель для похожей задачи проверен для
   локальной LLM), но **блокирован одним конкретным шагом на стороне владельца**
   (гипервизор Windows + перезагрузка), который дешевле снять, чем разбираться с
   неопределённой тарификацией Cloud.ru.
5. Вариант А остаётся разумным **если** станция окажется постоянно недоступна для батчей
   (владелец не готов её включать по расписанию) — тогда нужен явный тестовый прогон
   одного альбома на Cloud.ru с биллинг-консолью открытой до и после, прежде чем переносить
   всю библиотеку. Без этого теста фраза «укладывается в free tier» остаётся гипотезой,
   а не фактом.

**Условие «делать вариант А, если…»:** тестовый прогон одного альбома (≈50–100 фото)
на Cloud.ru показывает суммарный расход ≤ половины месячного ГБ·часового лимита
(≤ 25 ГБ·ч) за один такой прогон **и** секретный/basic-auth URL подтверждённо не даёт
доступ без знания секрета. Если тест этого не подтверждает — Вариант А закрывается в
пользу Б или В по решению владельца, а не переоценивается повторно на тех же
неподтверждённых цифрах.

## 9. EN summary

Task E6 asks whether Immich's machine learning (CLIP semantic search + ArcFace-family face
recognition, both confirmed via docs.immich.app and the Hugging Face model cards, 2026-09-20)
can run within Cloud.ru Container Apps' free tier, per owner decision D4: Cloud.ru is
acceptable *only if it fits the free tier*, and the risk of preview images leaving home is
accepted *conditional on that*. The free-tier numbers already noted (unverified) in the plan
are now **confirmed** against Cloud.ru's own docs: Container **Services** (what a persistent
Immich ML HTTP endpoint needs) get **25 vCPU·h + 50 GB·h/month** free; Container **Jobs**
(a separate pool, used by the unrelated D3 watchdog) get 5 vCPU·h + 10 GB·h — the two do not
compete for quota.

For our library (7098 assets, 6686 photos + 412 videos, CLAUDE.md 2026-08 measurement), raw
compute for a one-time backfill is estimated (generic public CPU benchmarks for CLIP ViT-B/32
+ ArcFace, **not measured on our hardware**, explicitly flagged) at roughly 0.6–3.0 vCPU-hours
— comfortably inside the 25 vCPU-hour budget. The real risk is the **GB-hour** side: if
Cloud.ru bills by container uptime (allocated RAM × wall-clock the instance stays warm) rather
than by CPU load — which is typical for this class of serverless platform but **not confirmed
for Cloud.ru specifically** — a backfill paced by Jetson's own upload/job-queue rhythm could
keep a 2–4 GB container warm far longer than its actual compute time, eating into or exceeding
the 50 GB-hour monthly ceiling. Exact overage pricing was not found in Cloud.ru's public docs
either. Cold start also matters beyond backfill: live text search hits the same ML service
synchronously, so if the container scales to zero between searches (confirmed platform
behavior), the first search after idle time will incur a start-up delay of unverified but
plausibly multi-second-to-tens-of-seconds duration.

Endpoint security is weaker than it looks: Immich's ML service ships with **no authentication
at all** (confirmed, verbatim from official docs), and Cloud.ru's built-in container
"Authorization" option requires interactive/IAM login — incompatible with how Immich calls a
remote ML URL. No IP-allowlist or private-network path usable from a physical device behind
double NAT was found. The realistic fallback is a secret, unpublished URL, optionally with
basic-auth embedded in the URL — untested against Immich's HTTP client.

The workstation-batch alternative (Option B) avoids the privacy question entirely: nothing
leaves home, using the same reverse-tunnel pattern already proven for the local LLM
(`ssh -R` to `172.17.0.1`, 0.637 s round trip, per CLAUDE.md). It is currently blocked by one
concrete, already-diagnosed owner-side step (Windows hypervisor disabled, deferred by the
owner to 2026-09-13, not re-checked by this document) rather than by unresolved cloud pricing
or auth questions. Immich's core app (upload, viewing, albums) keeps working when the ML
backend — whether Cloud.ru or the workstation — is offline; only search/face jobs queue and
retry (confirmed via Immich's issue tracker).

**Recommendation:** default to Option B (workstation batch over the tunnel) once the
hypervisor blocker is cleared; treat Option A (Cloud.ru) as a conditional fallback gated on an
explicit single-album test with the Cloud.ru billing console open before and after — not as
the default path — because its two open numbers (uptime-based GB-hour billing, and whether a
secret/basic-auth URL actually holds) are currently unverified, not merely unfavorable. Option
C (no ML) stays the honest fallback if neither A nor B is exercised: the family loses semantic
search and automatic face grouping, keeps everything else.

**Open for the owner:** hypervisor blocker status today; whether/when to run the single-album
Cloud.ru test; explicit acceptance of the weaker-than-expected endpoint protection if Option A
is chosen; E5 (spend alert) must land before any live Option A run per the existing queue.
