## 2. Что закрыто за этот день

### 2.1. ✅ Системные алерты в семейный чат заработали

`POST /v1/talk/notify` — документированный способ слать в чат «диск заполняется»,
«контейнер перезапустился» — **не работал никогда**. Дефект оказался двойным:

| # | Причина | Симптом |
|---|---|---|
| 1 | `_ocs_post` слал `json=`, а OCS принимает только форму | `404 / 998 "Invalid query"` |
| 2 | базовый URL указывал на **v4**, но чат в spreed живёт только в **v1** | `404` даже с правильной формой |

Накануне была починена только отправка бота, и работала она случайно: URL там
собирался вручную сразу с `v1`, поэтому обходил обе проблемы разом — и вторая
осталась незамеченной. Исправлено централизованно: `_talk_url()` и `_ocs_post()`
принимают версию API, чат ходит в `v1`, дублирование из бота убрано.

Проверено вживую, все три пути:

```
POST /v1/talk/notify → {"sent":true,"room_name":"Бобик — Алексей","message_id":116}
нас пинг             → 🏓 pong · uptime 1d 13h 33m
@бобик …             → 🐕 Да.
```

**Что это открывает:** Фазу E Talk-роадмапа — алерты о диске и USB можно увести
из Telegram (где их видит один человек) в семейный чат. Технически всё готово.

### 2.2. ✅ Канал фотографий наружу закрыт обратно

`LLM_ALLOW_IMAGE_ANALYSIS` возвращён в `false` на устройстве. Флаг включали ради
эксперимента с ретушью через GigaChat; эксперимент ответил на свой вопрос —
**провайдер фотографии не редактирует вообще**. Открытый канал, по которому
настоящие семейные снимки уходили в Сбер, не покупал ничего.

```
env в контейнере          → false
POST /v1/image/edit       → 403 "image analysis is disabled by policy"
@бобик ответь одним словом → 🐕 да        ← текст не пострадал
```

Третья строка была важна: нужно было убедиться, что закрыты именно фото, а не
разговор целиком.

### 2.3. ✅ Vostro: L0 пройден, роль пересмотрена

Ноутбук проверен вживую вместо доверия плану. Три результата, из них два —
против плана.

**Блокер снят.** Исходящий TCP/22 на VPS работает: `95.163.176.103:22` отвечает
баннером `OpenSSH_9.6p1`. PyPI, GitHub, HuggingFace — 200.

**Роль изменилась.** CUDA нет (Intel HD 520 + AMD R5 M230), 2 ядра без turbo,
3.7 ГБ RAM, и машину уже делит второй проект владельца, которому нужен отзывчивый
сервис. ML-роль снята: два ядра нельзя занять наполовину. Взяты сильные стороны —
**825 ГБ и расположение в другом здании**: off-site бэкап и внешний сторож.

**Найдена ловушка.** С ноутбука `172.29.172.1` ведёт на **постороннюю машину**:

```
с рабочей станции → OpenSSH_9.6p1   ← наш VPS
с ноутбука        → OpenSSH_8.9p1   ← чужой хост
```

Причина: `awg0` поднят (10.8.1.26), но маршрутов через него нет — запрос уходит
в чужой шлюз. Принадлежность хоста проверять **баннером**, а не пингом.

### 2.4. ✅ Появился канал между двумя проектами владельца

Два проекта делят ноутбук и VPS, а их сессии друг друга не видели. Цена этого
вскрылась в тот же день:

- соседний проект **больше месяца стоял на блокере, которого нет** — ждал
  доступности `193.8.215.130`, то есть **нашего старого адреса**, заблокированного
  провайдерами РФ с 06.08;
- его runbook собирался занять на VPS порт **`10022`**, который держит обратный
  туннель Jetson. Занял бы — Jetson потерял бы единственный путь управления.

Оба факта были известны — просто не тому агенту. Это **проблема общего состояния**,
а не удалённого управления, поэтому сделана «забирающая» доска
`E:\agent_coordination\` (вне git) + хуки `SessionStart` / `UserPromptSubmit`
в обоих проектах. Никто не пишет в чужую сессию; факты забираются сами.

Долгоживущий реестр общих ресурсов — `HOST_CONTRACT.md` **на самом ноутбуке**.

## 4. Грабли, добавленные в этот день

Все — из практики, не из документации:

1. **`172.29.172.1` — не адрес, а «кто окажется по нему в текущей сети».** Проверять баннером.
2. **`ffmpeg` съедает stdin** и вместе с ним остаток скрипта, переданного через `ssh "bash -s"`. Ставить `-nostdin`. Родня `sudo -S` + heredoc.
3. **Порты VPS — общий ресурс** с другим проектом. Сверяться с `ss -tlnp` до захвата.
4. **Консоль Windows — `cp1251`.** Печать кириллицы или даже стрелки `→` из Python роняет команду `UnicodeEncodeError`. Для машинного вывода — `ensure_ascii=True`.
