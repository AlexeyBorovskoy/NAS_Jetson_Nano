## 1. Методика: что, где и как мерили

**Железо и изоляция.** Замер шёл на самом Jetson (не на эмуляторе и не на Kaggle) —
это единственный способ получить число, которое проект вправе назвать RTF/памятью
именно этого устройства (Cortex-A57, без GPU в контейнерах). Инструменты ставились
через `apt`/`pip` внутри одноразовых контейнеров на базе уже присутствовавшего на
устройстве образа `python:3.12-slim` (arm64, был в `docker images` до начала работы —
в бюджет закачки не входит). Каждый контейнер — `--rm --memory=512m --cpus=2`,
жил секунды-минуты, исчезал сам. Ни один из 14 боевых контейнеров не трогался
(проверено: список имён до/после идентичен, см. §6).

**Модели (скачаны на Jetson, суммарно ~223 МБ трафика — в лимите 400 МБ):**

- **Vosk small-ru** (`vosk-model-small-ru-0.22.zip`) — 46.2 МБ. Официальный хост
  `alphacephei.com` оказался **недостижим с домашнего интернета Jetson** во время
  замера: TLS-рукопожатие обрывалось по таймауту и по HTTP, и по HTTPS (проверено
  дважды, включая 25-секундный таймаут) — при этом `google.com` и `huggingface.co`
  отвечали нормально. Взято зеркало официального zip-архива —
  `huggingface.co/localstack/vosk-models` (тот же файл, размер совпадает с
  документированным на `alphacephei.com`, ~45 МБ). Формат — оригинальный Kaldi
  (`am/`, `conf/`, `graph/`, `ivector/`), не ONNX-конверсия. Лицензия Apache 2.0.
- **whisper.cpp tiny** (`ggml-tiny.bin`, мультиязычная, fp16) — 77.7 МБ, с
  `huggingface.co/ggerganov/whisper.cpp` (официальный источник, доступен напрямую).
  Рантайм — исходники whisper.cpp собраны на самом устройстве (`cmake` + `make`,
  ~7 минут wall-clock на 2 ядрах в контейнере), бинарь `whisper-cli`. Лицензия MIT.

⚠️ **Отдельная находка, не по теме STT:** домен `github.com` (сам апекс-домен) тоже
не открывался с этой сети (TLS timeout), при этом `raw.githubusercontent.com`,
`codeload.github.com`, `objects.githubusercontent.com` и `pypi.org` работали
без проблем — то есть блокировка точечная, по конкретным доменам
(`alphacephei.com`, `github.com`), а не общий сбой интернета. Похоже по характеру
на уже задокументированную в проекте DPI-фильтрацию (`vps-xray-version-and-dpi-fragmentation`
в памяти), но это отдельный путь (домашний ISP, не VPS) — не расследовалось глубже,
фиксируется как факт для будущего.

**Тестовый набор (публичный, без семейных голосов, ~1.4 МБ):**
15 коротких фраз (1.25–4.45 с) из **тестового среза Golos** (Сбер, farfield-домен) —
зеркало `huggingface.co/datasets/bond005/sberdevices_golos_100h_farfield`, сплит
`test`, записи 0–14, получены через `datasets-server.huggingface.co` (публичный API,
без авторизации), WAV 16 кГц моно, с эталонным текстом в метаданных. Оригинальный
`SberDevices/Golos` на HF оказался пустым репозиторием (только README, без файлов) —
поэтому использовано стороннее зеркало реальных данных; лицензия самого зеркала
отдельно не перепроверялась (**НЕ ПРОВЕРЕНО** для конкретно этого HF-репозитория;
лицензия оригинального корпуса Golos — открытая для исследований и коммерческого
использования, подтверждено в `VOICE_MESSAGES_RESEARCH_2026-09-20.md` §4). Kaggle не
понадобился — доступ к данным и к железу совпал на одном устройстве.

Дополнительно — **2 более длинных файла** (11.4 с и 26.2 с), склеенные из 3 и 7 коротких
образцов через `ffmpeg concat`, чтобы отделить «модель грузится медленно» от «модель
декодирует медленно» на файлах, близких по длине к реальному голосовому Telegram (5–30 с).

**Целевой сценарий** («бобик, закачки» и т.п.) — в открытых наборах такой фразы нет.
Синтезировано 3 фразы через `espeak-ng` (ru, роботический голос) — **это не естественная
речь**, результат ниже помечен как слабый/индикативный сигнал, а не как замер качества
на реальном голосе.

**Что и как измерялось:**
- Время и RTF — `time.time()` вокруг вызова движка (Vosk: `KaldiRecognizer` в Python,
  модель грузится один раз на весь батч; whisper.cpp: отдельный процесс `whisper-cli`
  на каждый файл — модель грузится заново на каждый вызов, это часть замера, не баг).
- Память — `/usr/bin/time -v`, поле `Maximum resident set size`, на весь прогон.
- WER — собственный скрипт (нормализация: нижний регистр, без пунктуации; расстояние
  Левенштейна по словам) — не библиотека `jiwer`, задокументировано как собственная
  реализация, не эталонный инструмент.
- Конвертация OGG/Opus → WAV 16 кГц моно — `ffmpeg` против `opusdec` (пакет
  `opus-tools`), замерены и время (батч из 15 файлов), и размер установки (`dpkg`,
  `Installed-Size`).

## 3. Качество на целевых фразах (синтетика, слабый сигнал)

3 фразы синтезированы `espeak-ng` (ru, робот-голос) — **не настоящий голос**, только
проверка «не ломается ли пайплайн на команде с позывным»:

| Фраза (эталон) | Vosk small-ru | whisper.cpp tiny |
|---|---|---|
| «бобик закачки» | «полдник на краски» | «Бомик на кашке.» |
| «бобик скачай эту ссылку» | «кто тут цикл» | «Бобикская шаилетус» |
| «бобик какая сегодня погода» | «волге какая сегодня погода» | «Бомик Какая, сегодня, а подгонда.» |

Оба движка **не справились с роботическим TTS** — ожидаемо, `espeak-ng` даёт
неестественную просодию, которую акустические модели, обученные на живой речи, плохо
узнают. Любопытная деталь: whisper.cpp во всех 3 случаях уловил что-то похожее на
«бобик» («Бомик»/«Боби»), Vosk — ни разу; зато Vosk дважды из трёх верно распознал
хвост «какая сегодня погода» — частую бытовую фразу, а whisper исказил её везде.
**Вывод по этой части — не делать**: выборка синтетическая, 3 фразы, выводы о
поведении на реальном голосе семьи отсюда не следуют. Нужен настоящий тест на живом
голосовом (вне этого захода — собственный голос не записывался, в наборе не было
семейных данных по прямому требованию задания).

## 4. Рекомендация с обоснованием

**Победитель по всем замеренным числам — Vosk small-ru.** Основание:

1. **Скорость.** Vosk на 2 ядрах Cortex-A57 стабильно быстрее реального времени
   (RTF 0.35–1.25, то есть 5-секундное голосовое обрабатывается за ~2–4 с). whisper.cpp
   tiny — **медленнее реального времени почти везде**: на коротких фразах (характерных
   для Telegram-команд вида «бобик, закачки») RTF доходил до **10×** (13-секундная фраза
   на 1.3 с звука); даже на 26-секундном файле, ближе к верхней границе целевого
   диапазона 5–30 с, RTF остаётся 1.38 — то есть 26 секунд голосового обрабатывались бы
   **36 секунд**. При уже расписанном бюджете таймаутов цепочки (`TALK_BOT_LLM_TIMEOUT=150`
   с у шлюза, правило «таймаут вызывающего строго больше вызываемого» из `CLAUDE.md`) это
   означает переработку всего бюджета времени ради одного движка — Vosk этой проблемы
   не создаёт.
2. **Качество.** WER Vosk 17.07 % против 62.20 % у whisper.cpp tiny на одном и том же
   наборе — разница не на проценты, а в разы. whisper.cpp tiny на русском на этом
   железе (fp16, без квантования, мультиязычная модель) галлюцинирует целыми словами
   («что делайте, что они ченивают шелки, а с собаком» вместо «что делать если родители
   не разрешают взять собаку») — это не отдельные опечатки, а разваленный смысл фразы,
   непригодный для передачи в LLM-шлюз как команды.
3. **Память и размер** — паритет или небольшое преимущество Vosk (244.8 МБ пик у Vosk
   против 178.0 МБ у whisper, но у whisper память мерена по отдельным короткосуточным
   процессам, а не по одному долгоживущему воркеру — в реальном сервисе, где модель
   держится в памяти постоянно, а не перезагружается на каждый файл, цифры сблизятся;
   и в любом случае оба укладываются в предполагавшийся бюджет 192–320 МБ из
   `VOICE_MESSAGES_RESEARCH_2026-09-20.md`).
4. Конвертация OGG→WAV — рекомендация подтверждена: **`opus-tools`, не `ffmpeg`** —
   почти в 9 раз меньше на диске и в 4.7 раза быстрее на этой конкретной задаче
   (конвертация, а не общая обработка видео/аудио, для которой ffmpeg и существует).

**Итоговая рекомендация:** заменить в дальнейшем планировании первый вариант из
`VOICE_MESSAGES_RESEARCH_2026-09-20.md` (там был предложен whisper.cpp tiny первым
кандидатом, гипотетически, до замера) на **Vosk small-ru как основной, а не
запасной вариант**. Гипотеза «whisper мультиязычный — качество на русском под
вопросом» из исследования — **подтвердилась замером**, а не осталась гипотезой.

## 5. Риски и что осталось непроверенным

- 🟡 **Тестовый набор маленький (15 фраз) и не бытовой в точности** — это голосовые
  команды умной колонке Сбера (farfield-домен Golos), не голосовые сообщения близко
  сидящему Telegram-боту (ближе к «close-talk», без дальнего микрофона). Направление
  различия неизвестно — возможно, реальные Telegram-голосовые (с телефона, близко ко
  рту) окажутся даже чище, чем farfield-запись. Не измерено.
- 🟡 **Целевой сценарий (позывной «бобик» + команда) проверен только синтетическим
  TTS**, что признано слабым сигналом уже в §3 — нужен тест на настоящем голосе, вне
  рамок этой задачи (запрещено использовать семейные записи).
- 🟡 **WER — собственный скрипт, не `jiwer` или другой стандартный инструмент.**
  Числа воспроизводимы (нормализация простая: регистр + пунктуация), но не сверены
  с общепринятой библиотекой — расхождение возможно на десятые доли процента, не на
  порядок.
- 🟡 **Память whisper.cpp измерена по короткоживущим процессам** (перезагрузка модели
  на каждый вызов CLI), а не по демону с моделью, загруженной один раз — в проде
  ожидаемо ниже пиковое потребление, но выше задержка на первый вызов после старта
  контейнера. Не измерялось.
- 🟡 **whisper.cpp base/small и faster-whisper не тестировались** — по итогам замера
  `tiny` в этом заходе смысла нет: если `tiny` уже даёт RTF > 1 и WER 62 %, более
  тяжёлые модели того же семейства будут медленнее, а выигрыш в качестве неизвестен
  без отдельного замера. Решение по ним — не в этом бейк-оффе.
- 🟡 **Блокировка `alphacephei.com` и `github.com`** с домашнего интернета Jetson
  (см. §1) — зафиксирована как наблюдение по состоянию на 2026-09-20, причина не
  расследовалась (не входило в задачу), может быть временной.
- 🟢 **Закрыто этим замером:** гипотеза «whisper.cpp tiny — первый кандидат» из
  `VOICE_MESSAGES_RESEARCH_2026-09-20.md` — отклонена по числам, не по мнению.

## 7. EN summary

Bake-off of two local Russian STT engines, run directly on the production Jetson Nano
(Cortex-A57, no GPU used by containers), inside disposable `--rm --memory=512m --cpus=2`
containers, using a 15-phrase public test slice of Sber's Golos corpus (farfield domain,
mirrored on Hugging Face as `bond005/sberdevices_golos_100h_farfield` — the original
`SberDevices/Golos` HF repo turned out to be empty). Official Vosk host `alphacephei.com`
was unreachable from the device's home ISP during this run (TLS timeout on both HTTP and
HTTPS; `github.com` apex domain was equally unreachable while its CDN subdomains worked
fine) — an HF mirror of the same official zip was used instead, verified by matching size.

**Result: Vosk small-ru wins decisively on every measured axis.** Real-time factor
0.35–1.25 (faster than real time) vs whisper.cpp tiny's 1.38–9.95 (up to 10× *slower*
than real time on short clips typical of a Telegram voice command); word error rate
17.07% vs 62.20% on the same 15 phrases (whisper.cpp tiny hallucinated whole words in
Russian); Vosk's WER degrades to 19.51% after a realistic OGG/Opus 32kbps round-trip,
still far ahead of whisper. Peak RSS: Vosk 244.8 MB for a whole 15-file batch (model
loaded once), whisper.cpp tiny 178.0 MB peak per short-lived CLI invocation (model
reloaded every call — a different usage pattern, noted as a caveat). For OGG→WAV 16kHz
mono conversion, `opus-tools` (`opusdec`) beat `ffmpeg` on both install footprint
(≈3.8 MB vs ≈34.8 MB of apt dependencies) and batch speed (1.47s vs 6.98s for 15 files).

This overturns the pre-measurement hypothesis in `VOICE_MESSAGES_RESEARCH_2026-09-20.md`,
which had proposed whisper.cpp tiny as the first candidate — that hypothesis is now
rejected by measurement, not by opinion. Recommendation: **Vosk small-ru as the primary
STT candidate**, `opus-tools` for the OGG conversion step. Caveats: the 15-phrase test set
is a smart-speaker farfield corpus, not a close-talk phone recording like real Telegram
voice messages; the target wake-word scenario ("бобик, ...") was only tested with robotic
espeak-ng TTS (both engines struggled with it — a weak signal, not a real-voice result);
WER was computed with a hand-written Levenshtein script, not a standard library. Cleanup
confirmed: temp directory removed, zero leftover `bench_*` containers, container count
back to 14, disk usage identical to baseline (14G/229G), available memory 1732 MB (never
dropped below the 600 MB stop threshold during the run).
