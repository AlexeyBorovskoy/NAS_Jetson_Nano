## 1. Зачем

Владелец (13.10): «Хочу, чтобы на Jetson работало решение, которое пишет полностью все подробные логи,
и ты мог всегда восстановить причины различных нештатных ситуаций».

Что подводило до сих пор (всё — по журналам проекта):

| Случай | Чего не хватило |
|---|---|
| Сбросы 17.08 и 18.09 | Нечем отличить пропадание питания от сторожа PMIC — записано как «неизвестно» |
| Три выключения 29.09–11.10 | Узнали, что выключал владелец, только спросив его |
| Зависание `ntfs-3g` 20.09 | Не было снимка зависших процессов и истории операций диска |
| Перезапуск микросервисов Immich 13.10 03:20 | Понятно только потому, что ведущий был рядом и читал события Docker в ту же минуту |
| Смена букв дисков после загрузки 12.10 | Обнаружена случайно; снимка «какой диск какой буквой» при загрузке нет |

**Критерий успеха:** для каждого класса сбоев (раздел 6) одна команда `nas-why` выдаёт хронологию и вердикт
с пометкой уверенности — или честное «данных нет»; проверено на подставных данных и приёмкой на Jetson (раздел 9).

## 2. Решения владельца (13.10)

1. Всё хранится **на устройстве**, наружу ничего не уходит (ни VPS, ни станция).
2. Глубина **ступенчатая:** подробности — последние дни на SSD, всё остальное — год.
3. **Всё на SSD**; раз в неделю — архив на HDD, чтобы SSD не забивался историей.
4. Подход **А**: свой лёгкий сборщик + команда `nas-why` (не готовый стек, не Grafana/Loki/Prometheus).
5. **Журналы всех контейнеров** — полностью, год; у контейнеров семьи — с вырезанием русского текста.

## 3. Что уже есть (замер 13.10) и факты, на которые опирается проект

- Журнал systemd: `Storage=persistent`, `SystemMaxUse=200M` на SD — заполнен (212 МБ), глубина ≈ 25 дней (5 загрузок).
  rsyslog дублирует его в `/var/log` (336 МБ на SD).
- Docker: `json-file` **без ограничения размера**; за сутки все контейнеры пишут ≈ 6,5 МБ (Nextcloud 4,2).
  В журналах API и шлюза за сутки **нет ни одной строки с кириллицей** (99 % — проверки здоровья); у распознавания речи — 1.
- Датчик питания INA3221 (`/sys/bus/i2c/drivers/ina3221x/6-0040/iio:device0`, три канала) читается **только от root**.
- ramoops/pstore: в ядре зарегистрирован (`Registered ramoops as persistent store backend`), `/sys/fs/pstore` пуст —
  при прошлых сбросах паники ядра не было.
- `/dev/watchdog` есть, `RuntimeWatchdogSec` в systemd не настроен.
- Буквы дисков меняются между загрузками (REL-11): ключ — `/dev/disk/by-id`, не `sda`/`sdb`.
- Хост: Python 3.6.9, SQLite 3.22, systemd 237 (правила юнитов — `tests/unit/test_systemd237_units.py`).
- Свободно: SSD ≈ 190 ГБ, HDD ≈ 396 ГБ, SD ≈ 33 ГБ; RAM — ≈ 1 ГБ в обычном режиме.

## 4. Состав

```
            ┌────────────────────── nas_jetson_nano-blackbox.service (root, запертая) ─────────────────────┐
 sysfs/proc │ fast (1 с) ─► sample          procs (10/60 с) ─► proc_snapshot     heartbeat (10 с, fsync)   │
 Docker API │ events (поток) ─► event (+хвост журнала контейнера)   logs (60 с) ─► containers/*.log.gz     │
 journald   │ journal (5 мин) ─► journal.log              probes (60 с) ─► event (сеть, монтирования)      │
            └───────────────► /mnt/storage/blackbox/hot/<день>/  +  catalog.db  ◄── nas-why ───────────────┘
 загрузка:  nas_jetson_nano-blackbox-boot.service ─► boots/<boot_id>/ + вердикт прошлой загрузки ─► алерт D2
 неделя:    nas_jetson_nano-blackbox-archive.timer ─► /mnt/hdd2tb/backups/blackbox/<год>/blackbox-ГГГГ-Wнн.tar.xz
```

### 4.1. Сборщик `nas-blackbox` (одна служба, один процесс Python 3.6, только стандартная библиотека)

| Цикл | Частота | Что пишет |
|---|---|---|
| fast | 1 с | Питание: напряжение, ток, мощность трёх каналов INA3221; температуры всех зон; загрузка и частота CPU; `MemAvailable`, подкачка, ZRAM; `loadavg`; по каждому диску (ключ by-id): операции чтения/записи, секторы, занятость; `eth0`/`docker0` байты |
| procs | 60 с; **10 с при аномалии** | Топ-10 процессов по CPU и по RSS (имя, контейнер, команда до 90 символов), **все процессы в D-state** с `wchan`. Аномалия: есть D-state, или `MemAvailable` < 300 МБ, или `load1` > 6, или подкачка растёт > 50 МБ/мин |
| heartbeat | 10 с | Файл `heartbeat` (boot_id, время, последний замер питания): запись во временный файл + `fsync` + `rename` + `fsync` каталога |
| events | поток | События Docker через сокет `/var/run/docker.sock` (без отдельного процесса `docker`): `die`, `oom`, `kill`, `stop`, `start`, `restart`, `health_status` — с кодом выхода и атрибутами. На `die`/`oom`/`unhealthy` — последние 200 строк журнала контейнера (с маскированием, 4.3) |
| logs | 60 с | Дочитывание файлов `json-file` всех контейнеров с запомненной позиции (inode + смещение; ротация и усечение — с начала нового файла). Проверки здоровья (`GET /health`, `/healthcheck`, `/status.php` с кодом 200) — не строками, а счётчиком в минуту |
| journal | 5 мин | `journalctl --after-cursor=<c> --show-cursor -o short-iso-precise` → дописать в `journal.log` дня, курсор — в `catalog.db` |
| probes | 60 с | Шлюз (`ping -c1 -W1`), DNS (разрешение с таймаутом), туннель VPS (`nasa-tunnel` активен + установленное соединение к VPS по `/proc/net/tcp`), прокси Telegram (TCP 172.17.0.1:1080), монтирования SSD/HDD (`timeout 5 stat -f`) |
| rollup | 60 с | Минутные min/avg/max ключевых величин → `catalog.db` |
| guard | 60 мин | Предел «горячего» на SSD (раздел 5.3) |

Проверка монтирования HDD — **только в отдельном процессе с таймаутом**, и новый не запускается, пока предыдущий не
вернулся: зависший `ntfs-3g` держит процесс в D-state навсегда, и иначе их копилось бы по одному в минуту.
Событие «монтирование не отвечает с ЧЧ:ММ» пишется один раз.

### 4.2. Снимок при загрузке `nas-blackbox-boot` (oneshot)

`After=local-fs.target docker.service`, `Wants=` (не `Requires=`) монтирования SSD: если SSD не поднялся, снимок
пишется в запасной каталог на SD (5.4). Содержимое `boots/<boot_id>/`:
`uname -a`, `/etc/nv_tegra_release`, полный `dmesg`, строка `PMC reset source`, `lsblk` с моделями, серийниками и UUID,
`ls -l /dev/disk/by-id`, `lsusb -t`, `/proc/mounts`, копии файлов `/sys/fs/pstore/*`, последние 300 строк журнала
прошлой загрузки, `docker ps -a` (имена, образы, статус — **не** `docker inspect`), и **вердикт прошлой загрузки** (раздел 6).

### 4.3. Маскирование

- **Все контейнеры и журнал:** токены и ключи (`token=`, `Authorization:`, `password=`, `api_key`, `Bearer …`,
  строки вида `<tenant>:<keyId>`) → `<скрыто>`; те же образцы, что у `scripts/security/check_no_secrets.sh`.
- **Контейнеры семьи** (`homecloud_nasa_api`, `homecloud_llm_gateway`, `homecloud_stt` — список в конфиге):
  подряд идущие русские слова длиной от трёх → `<текст скрыт>`.
- Никогда не сохраняются: содержимое `.env`, вывод `docker inspect`, тела HTTP-запросов.

### 4.4. `nas-why` (команда)

```
nas-why --boot -1 [--short]           # как закончилась прошлая загрузка (--short — для алерта, ≤ 6 строк)
nas-why --since "2026-10-13 03:15" [--until …]
nas-why --container homecloud_immich_microservices [--since …]
```
Читает «горячее» на SSD и `catalog.db`; за старые дни сам распаковывает нужные дни из архива HDD в
`/mnt/storage/blackbox/tmp/` (с таймаутом) и удаляет после ответа. Вывод: хронология (источник, время, строка) +
вердикты (раздел 6) с уверенностью **факт / вероятно / неизвестно**.

### 4.5. Связи с существующим

- **Алерт D2** (`nas_jetson_nano-boot-alert`): добавляет вывод `nas-why --boot -1 --short` (таймаут 60 с;
  при ошибке — прежний текст). Убирается ссылка на `CLAUDE.md` и вопрос «выключали сами?» (хвост REL-1/REL-10).
- **Сторож OPS-1:** проверяет свежесть `heartbeat` — старше 2 мин при работающей службе → алерт «чёрный ящик молчит»
  (не чаще раза в час).
- Хостовые пути — через `/etc/nas-layout.env` (как `scripts/lib/layout.sh`), без литеральных `/home/admin` (SD-2).

## 5. Хранение

### 5.1. Раскладка

```
/mnt/storage/blackbox/                     (SSD)
  hot/<ГГГГ-ММ-ДД>/metrics.db              секундные замеры дня (sample, disk_sample)
  hot/<ГГГГ-ММ-ДД>/procs.db                снимки процессов
  hot/<ГГГГ-ММ-ДД>/containers/<имя>.log.gz журналы контейнеров (gzip, дописываемые блоки)
  hot/<ГГГГ-ММ-ДД>/journal.log(.xz)        копия журнала systemd
  boots/<boot_id>/                         снимки загрузок (год)
  catalog.db                               минутные сводки, события, загрузки, архивы (год)
  heartbeat                                последняя метка «жив»
  staging/, tmp/                           сборка архива, распаковка для nas-why
/var/lib/nas-blackbox/fallback/            (SD) только если SSD нет, ≤ 20 МБ
/mnt/hdd2tb/backups/blackbox/<ГГГГ>/       (HDD) недельные архивы + .sha256, год
```
Сутки — по UTC. День «закрывается» в 00:00 UTC: `journal.log` сжимается в `.xz`, файлы дня больше не меняются.

### 5.2. Данные (SQLite, WAL, пакетная запись раз в 10 с)

| Таблица | Где | Поля (кратко) |
|---|---|---|
| `sample` | metrics.db | `ts` (PK), `vin_mv`, `vin_ma`, `cpu_mw`, `gpu_mw`, `t_cpu`…`t_pmic` (×10 °C), `cpu_pct`, `freq_mhz`, `mem_avail_mb`, `swap_mb`, `zram_mb`, `load1×100`, `net_rx`, `net_tx` |
| `disk_sample` | metrics.db | `ts`, `disk_id` (by-id), `rios`, `wios`, `rsect`, `wsect`, `busy_ms` |
| `proc_snapshot` | procs.db | `ts`, `pid`, `comm`, `owner`, `cmd`, `state`, `wchan`, `cpu_pct`, `rss_mb` |
| `minute` | catalog.db | `ts`, min/avg/max: `vin_mv`, `cpu_pct`, `mem_avail_mb`, `swap_mb`, `t_cpu`; сумма операций дисков; счётчики проверок здоровья по контейнерам |
| `event` | catalog.db | `ts`, `source` (docker/probe/kernel/archiver/guard/boot), `kind`, `subject`, `severity`, `detail` (JSON) |
| `boot` | catalog.db | `boot_id`, `start`, `end`, `clean`, `last_heartbeat`, `reset_source`, `pstore`, `verdict`, `confidence` |
| `archive` | catalog.db | `week`, `path`, `sha256`, `first_day`, `last_day`, `created`, `verified` |

Оценка объёма: секундные ≈ 20–35 МБ/сутки, процессы ≈ 5–10, журналы контейнеров и системы (сжатые) ≈ 2 →
«горячее» за 14 дней ≤ 0,7 ГБ; `catalog.db` ≈ 200 МБ/год; архив на HDD ≈ 50–80 МБ/неделя (≈ 3–4 ГБ/год).
Цифры уточняются первой неделей работы.

### 5.3. Недельный архив на HDD (`nas-blackbox-archive`, воскресенье 05:30 UTC + ежедневный повтор, если есть долг)

1. Кандидат — ISO-неделя, последний день которой старше 7 суток; на SSD поэтому живёт от 7 до 14 дней.
2. Не стартует, если активны `nas_jetson_nano-immich-hdd-copy`, `nas_jetson_nano-config-backup`, `nasa-backup` или
   процесс `restic`, или HDD не отвечает (`timeout 5 stat -f`) — откладывает до следующего дня.
3. `tar` + `xz` в `staging/` с `nice`/`ionice -c3`, sha256.
4. Копия на HDD **одним файлом**: `timeout 1800 cp` во временное имя → `sync` → `rename`; затем
   `timeout 600 sha256sum` с HDD и сверка.
5. Только при совпадении — удалить дни недели с SSD и записать `archive` в `catalog.db`; иначе — ничего не удалять,
   событие + алерт; повтор завтра.
6. Удалить с HDD архивы старше 365 дней.
7. **Предохранитель SSD** (каждый час, в сборщике): «горячее» > 1 ГБ → удалять самые старые `metrics.db`
   (секундные), затем `procs.db`; **журналы и события — никогда**; событие + алерт.
8. Две пропущенные недели подряд → алерт «архив не уходит на HDD».

### 5.4. Если SSD нет

Сборщик пишет в `/var/lib/nas-blackbox/fallback/` на SD: снимок загрузки, `heartbeat` раз в 60 с, минутные сводки,
события; предел 20 МБ (кольцом). Когда SSD появляется — переносит накопленное в `catalog.db` и `boots/`.

## 6. Правила вердиктов

| Класс | Признаки → вердикт |
|---|---|
| Нештатная загрузка | Нет штатного выключения в прошлой загрузке. Есть `pstore` → **факт:** паника ядра (+ выдержка). Перед последним `heartbeat` вход 5 В < 4,75 В или ток у предела → **вероятно:** питание. Питание ровное до последней секунды → **вероятно:** внезапное пропадание питания или аппаратный сброс (различить нечем — так и пишется). Есть событие «выключение командой» (REL-10) → штатно. Перед смертью копились D-state / нулевой ввод-вывод / `MemAvailable` < 150 МБ → **вероятно:** зависание, затем сброс. Всегда — `PMC reset source` и время последнего признака жизни |
| Контейнер упал или перезапущен | Кто: сторож OPS-1 (строка в его журнале в ±2 мин), политика `restart`, `compose up` (событие `create` перед `start`). Код: 137 — убит (OOM, если флаг), 143 — SIGTERM, иначе — ошибка приложения. Журнал проверки здоровья, хвост журнала контейнера |
| Зависание диска | D-state с `wchan` из семейства `fuse`/`request_wait_answer`, ноль операций на этом диске ≥ 60 с, проба монтирования не вернулась |
| Нехватка памяти | Минимум `MemAvailable`, рост подкачки, `oom-kill`/`Killed process` в журнале ядра, процесс с наибольшим ростом RSS |
| Сеть и туннель | Какая проба падала: шлюз → домашняя сеть; DNS; туннель VPS → провайдер или блок адреса; прокси → Telegram |
| Перегрев | Температуры у порогов, снижение частоты |
| USB и диски | `error -71`, `I/O error`, `uas_eh`, переподключение; несовпадение «буква ↔ by-id» со снимком прошлой загрузки |

Пороги (4,75 В, 150/300 МБ, 60 с) — в конфиге; 4,75 В = 5 В −5 % (уточнить по базовой линии первой недели).
Нет данных за окно → **неизвестно: данных нет за <интервал>** (никогда не догадка).

## 7. Безопасность и бюджет

- Служба от root (датчик питания, `/var/lib/docker/containers`, `wchan`), но: `ProtectSystem=strict`,
  `ReadWritePaths=/mnt/storage/blackbox /var/lib/nas-blackbox`, `ProtectHome=read-only`, `NoNewPrivileges=yes`,
  `PrivateTmp=yes`, `MemoryLimit=64M`, `CPUQuota=10%`, `Nice=10`, `IOSchedulingClass=idle`;
  `Type=simple`, `Restart=on-failure`, `StartLimit*` в `[Unit]` (systemd 237).
- Бюджет: RSS ≤ 40 МБ (предел 64), CPU ≤ 5 % в среднем, запись на SSD ≤ 60 МБ/сутки, на SD в обычном режиме — ноль.
- Падение сборщика ни на что не влияет; его молчание видит OPS-1 (4.5).
- Файлы — `root:adm`, `0640`; `nas-why` — от root или участника `adm`.

## 8. Что не входит

Отправка за пределы устройства; веб-интерфейс; замена netdata; смена драйвера журналов Docker и ротация `json-file`
(нужен перезапуск `dockerd` — отдельное окно обслуживания); автоматическое лечение (только диагноз и алерт).

## 9. Проверка и приёмка

**До выката (в git):** тесты `tests/blackbox/` (pytest) на подставных данных: дерево sysfs INA3221 и терм-зон,
`/proc/*` (stat, diskstats, meminfo), поток событий Docker, файлы `json-file` с ротацией и усечением, вывод
`journalctl` с курсором, маскирование (токены; русский текст у контейнеров семьи и не у остальных), архиватор
(сверка sha256, отказ при активном задании HDD, ничего не удаляет при ошибке, предохранитель SSD) и **каждое правило
раздела 6 на синтетической хронологии**. Ворота: Python 3.6 (`vermin`), храповик (новые функции ≤ 40 строк, CC ≤ 10),
правила systemd 237; `tests/blackbox` добавляется в раздел тестов сервисов `preflight.sh`.

**Приёмка на Jetson (по слову владельца):**
1. Час работы: RSS ≤ 64 МБ, CPU ≤ 10 % (замер `scripts/quality/cpp1_probe.py`).
2. `docker restart` безобидного контейнера → `nas-why --container …` называет ручной перезапуск, код 143.
3. Остановка сборщика на 3 мин → дыра в `heartbeat` видна, OPS-1 прислал алерт.
4. Архиватор на тестовой неделе → архив на HDD, sha256 совпал, дни ушли с SSD.
5. Первая настоящая нештатная загрузка → вердикт в алерте D2.
Искусственное отключение питания — не здесь, а в испытаниях REL-4.

## 10. Выкат и откат

Выкат: файлы + юниты по runbook, `systemd-analyze verify`, включение служб, проверка «работает новый код» (правило №14).
Откат: `systemctl disable --now` двух служб и таймера; прежний текст D2 из резервной копии. Данные `/mnt/storage/blackbox`
удаляются только по решению владельца.

## 11. Исполнители

Ведущий — спецификация, план, ревью, выкат и приёмка. Sonnet — сборщик, снимок загрузки, архиватор, `nas-why`.
DeepSeek — тесты, английские пары документов. Секреты — никому.

## 12. Открытые вопросы (закрываются при реализации)

1. Имена каналов INA3221 на этом модуле (ожидаются `POM_5V_IN`, `POM_5V_GPU`, `POM_5V_CPU`) — прочитать от root.
2. Состоит ли `admin` в группе `adm` (иначе `nas-why` через sudo).
3. Порог питания — по базовой линии первой недели.
