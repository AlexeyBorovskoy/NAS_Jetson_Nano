1. Рекомендуемый стек

Для Windows я бы взял:

Уровень	Компонент	Назначение
Чат	Telegram / ваш существующий бот	интерфейс пользователя
Agent	локальный LLM / Claude / GigaChat	понимание команды
Протокол	MCP	управление инструментами
Оркестратор изображений	ComfyUI	выполнение AI-workflow
Основной редактор	Qwen-Image-Edit	интеллектуальное редактирование
Альтернатива	FLUX.1 Kontext	сложное редактирование
Апскейл	Real-ESRGAN	увеличение разрешения
Background	BiRefNet	удаление/выделение фона
Базовая обработка	OpenCV + Pillow	цвет, размер, EXIF, JPEG
Хранилище	локальная файловая система	исходники/результаты
Очередь	Redis, позднее	очередь тяжёлых задач

Главный элемент здесь — ComfyUI. Он выступает не как GUI для пользователя, а как движок выполнения графа обработки.

2. Основная модель — Qwen-Image-Edit

Я бы сейчас начал именно с Qwen-Image-Edit, а не с Kandinsky.

Qwen-Image — открытая модель класса 20B, а семейство Qwen-Image-Edit предназначено именно для редактирования существующих изображений. В документации заявлены, в частности, удаление/добавление объектов, изменение стиля, улучшение деталей и работа с позой.

Особенно важно для вашего сценария:

модель должна изменять существующую фотографию, а не генерировать новую фотографию по описанию.

Например:

Исходная фотография
        │
        ▼
Qwen-Image-Edit
        │
        ├── "убери людей справа"
        ├── "сделай небо более выразительным"
        ├── "сделай цвет естественнее"
        ├── "сделай фотографию в стиле travel magazine"
        └── "сделай мягкую glamour-ретушь лица"

При этом Qwen отдельно указывает на сохранение визуальной семантики исходного изображения при редактировании.

3. Я бы сделал MCP не слишком «умным»

Это принципиальный момент.

Не надо давать LLM один инструмент:

Лучше сделать специализированный API:

photo_analyze()
photo_enhance()
photo_retouch()
photo_remove_object()
photo_remove_background()
photo_replace_background()
photo_color_grade()
photo_upscale()

Тогда Agent сможет сам выбрать технологию.

Например пользователь пишет:

Удали мусорный контейнер справа и сделай фотографию немного светлее.

Agent:

photo_analyze
       ↓
photo_remove_object
       ↓
photo_enhance
       ↓
photo_compare

А если:

Сделай из этого нормальную фотографию с экскурсии.

Тогда:

       ↓
photo_enhance
       ↓
photo_upscale

5. Для портретов отдельный workflow

Лучше:

                     portrait

6. Для обычных фотографий я бы вообще не использовал генеративную модель постоянно

Это очень важно.

Если пользователь пишет:

Нет смысла запускать 20B diffusion model.

Лучше:

OpenCV
Pillow
Real-ESRGAN

А генеративную модель использовать только там, где действительно требуется семантическое изменение.

Получается:

                  MCP
                   │
                   ▼
             photo_analyze
                   │
        ┌──────────┼───────────┐
        ▼          ▼           ▼
    обычная      портрет     изменение
    обработка                 объекта
        │          │           │
        ▼          ▼           ▼

   Pillow                    / Flux
        │          │           │
        └──────────┼───────────┘
                   ▼
              Real-ESRGAN

Это будет намного быстрее и экономичнее по GPU.

7. Real-ESRGAN обязательно

Для финального этапа я бы поставил Real-ESRGAN.

Он предназначен именно для восстановления/увеличения изображений; поддерживает произвольный масштаб, тайлинг и отдельное улучшение лиц через GFPGAN.

Например:

Telegram photo
     ↓
2048 × 1365
     ↓
AI processing
     ↓
2048 × 1365
     ↓
Real-ESRGAN
     ↓
4096 × 2730

Но я бы не делал 4× всегда. Для фотографий обычно разумнее дать Agent выбор:

upscale = 1.5
upscale = 2
upscale = 4
8. BiRefNet

Для фона я бы добавил BiRefNet.

Он хорошо подходит для:

вырезания человека;
удаления/замены фона;
подготовки маски;
дальнейшего inpainting.

Есть локальные реализации BiRefNet, которые работают без отправки изображений во внешнее хранилище.

Тогда можно сделать:

Замени фон на красивый вечерний Париж.

Pipeline:

original
   │
   ▼
BiRefNet
   │
   ├── foreground
   └── mask
          │
          ▼
   Qwen-Image-Edit
          │
          ▼
      composite
9. А FLUX куда?

FLUX.1 Kontext я бы оставил вторым генеративным движком.

Он специально ориентирован на image editing и позволяет передавать исходную фотографию вместе с текстовой инструкцией. Открытая FLUX.1 Kontext [dev] существует, но имеет Non-Commercial License, поэтому для корпоративного продукта обязательно надо отдельно проверить лицензионные ограничения.

Поэтому для вашего проекта:

Qwen-Image-Edit — основной кандидат.

FLUX Kontext — дополнительный экспериментальный backend.

И MCP вообще не должен знать, какая модель работает:

photo_edit()
      │
      ▼
Image Engine
      │
      ├── qwen
      ├── flux
      └── future_model

13. Но есть один серьёзный вопрос — ваше железо

Здесь я бы пока не начинал установку Qwen-Image-Edit вслепую.

Qwen-Image-Edit — тяжёлая модель. Ваш ноутбук с 32 ГБ RAM и мобильной GPU, насколько я понимаю, не является хорошей машиной для комфортного запуска такой модели. В результате можно получить либо очень медленную обработку, либо необходимость агрессивной квантизации/offload.

Поэтому я бы разделил систему:

             Telegram
                 │

        │                 │
        ▼                 ▼

                     BiRefNet

То есть обычная обработка работает на вашем компьютере, а тяжёлые модели можно вынести на отдельную GPU-машину.

# Photo processing prompt (English)

1. Recommended stack

For Windows I would take:

Layer	Component	Purpose
Chat	Telegram / your existing bot	user interface
Agent	local LLM / Claude / GigaChat	command understanding
Protocol	MCP	tool orchestration
Image orchestrator	ComfyUI	running AI workflows
Primary editor	Qwen-Image-Edit	intelligent editing
Alternative	FLUX.1 Kontext	complex editing
Upscale	Real-ESRGAN	resolution increase
Background	BiRefNet	background removal/extraction
Basic processing	OpenCV + Pillow	color, size, EXIF, JPEG
Storage	local file system	sources/results
Queue	Redis, later	queue for heavy jobs

The key element here is ComfyUI. It acts not as a GUI for the user but as an execution engine for the processing graph.

2. The main model — Qwen-Image-Edit

Right now I would start with Qwen-Image-Edit, not with Kandinsky.

Qwen-Image is an open 20B-class model, and the Qwen-Image-Edit family is designed specifically for editing existing images. The documentation claims, among other things, object removal/addition, style change, detail enhancement, and pose work.

Especially important for your scenario:

the model must modify an existing photo, not generate a new photo from a description.

For example:

Source photo
        │
        ▼
Qwen-Image-Edit
        │
        ├── "remove the people on the right"
        ├── "make the sky more expressive"
        ├── "make the color more natural"
        ├── "make the photo look like a travel magazine"
        └── "apply soft glamour retouching to the face"

Qwen separately highlights preservation of the source image's visual semantics during editing.

3. I would not make the MCP too "smart"

This is a matter of principle.

Do not give the LLM a single tool:

edit_image(prompt)

Better to build a specialized API:

photo_analyze()
photo_enhance()
photo_retouch()
photo_remove_object()
photo_remove_background()
photo_replace_background()
photo_color_grade()
photo_upscale()
photo_edit()
photo_compare()

Then the Agent can pick the technology itself.

For example, the user writes:

Remove the trash container on the right and make the photo a bit brighter.

Agent:

photo_analyze
       ↓
photo_remove_object
       ↓
photo_enhance
       ↓
photo_compare

And if:

Turn this into a decent photo from the excursion.

Then:

photo_analyze
       ↓
photo_enhance
       ↓
photo_upscale

4. The most interesting one — photo_analyze

I would definitely build this tool.

The LLM receives the photo and first determines:

{

  "architecture": true,
  "sky": true,
  "low_light": true,
  "blur": false,
  "noise": "medium",
  "composition": "good"
}

After that the Agent picks the pipeline.

For example:

Excursion photo

       │
       ├── architecture = true
       ├── sky = true
       ├── people = 3
       └── low_light = true
              │
              ▼

              │

       ▼      ▼      ▼
     color   light  denoise
       │      │      │
       └──────┼──────┘
              ▼
          Real-ESRGAN

This is very important.

If the user writes:

There is no point in launching a 20B diffusion model.

Better:

This will be much faster and much cheaper on the GPU.

7. Real-ESRGAN is a must

For the final stage I would put Real-ESRGAN in place.

It is designed exactly for image restoration/upscaling; it supports arbitrary scale, tiling, and separate face enhancement via GFPGAN.

For example:

Telegram photo
     ↓
2048 × 1365
     ↓
AI processing
     ↓
2048 × 1365
     ↓
Real-ESRGAN
     ↓
4096 × 2730

But I would not always do 4×. For photos it is usually more sensible to give the Agent a choice:

upscale = 1.5
upscale = 2
upscale = 4

8. BiRefNet

For backgrounds I would add BiRefNet.

It is a good fit for:

cutting out a person;
removing/replacing the background;
preparing a mask;
subsequent inpainting.

There are local BiRefNet implementations that work without sending images to external storage.

Then you can do:

Replace the background with a beautiful evening Paris.

Pipeline:

original

          ▼

9. And where does FLUX fit?

I would keep FLUX.1 Kontext as the second generative engine.

It is specifically aimed at image editing and lets you pass the source photo together with a text instruction. The open FLUX.1 Kontext [dev] exists but carries a Non-Commercial License, so for a corporate product the licensing restrictions must be checked separately.

Therefore, for your project:

Qwen-Image-Edit — the primary candidate.

FLUX Kontext — an additional experimental backend.

And the MCP should not know at all which model is doing the work:

photo_edit()
      │
      ▼
Image Engine
      │
      ├── qwen
      ├── flux
      └── future_model

13. But there is one serious question — your hardware

Here I would not start installing Qwen-Image-Edit blindly.

Qwen-Image-Edit is a heavy model. Your laptop with 32 GB RAM and a mobile GPU is, as far as I understand, not a good machine for running such a model comfortably. The result would be either very slow processing or the need for aggressive quantization/offload.

So I would split the system:

             Telegram
                 │
                 ▼
              MCP
                 │
        ┌────────┴────────┐
        │                 │
        ▼                 ▼
     CPU/GPU           GPU Server
  simple processing    generative AI
        │                 │
        ▼                 ▼
 OpenCV/Pillow       Qwen-Image-Edit
 Real-ESRGAN         FLUX Kontext
                     BiRefNet

That is, ordinary processing runs on your computer, while the heavy models can be moved to a separate GPU machine.

My final choice

MVP:

MCP Server: Python
API: FastAPI
Workflow engine: ComfyUI
Primary AI model: Qwen-Image-Edit
Object removal / semantic editing: Qwen-Image-Edit
Background: BiRefNet
Upscale: Real-ESRGAN

Queue: without Redis at first, then Redis
Interface: your Telegram bot
LLM: the same Agent that currently drives your MCP
All photos: local by default
Cloud APIs: only as a fallback backend.

This gives you not an "image generation bot" but a universal MCP Photo Service, which can later be connected not only to Telegram but also to Cursor, Claude Code, a web interface, and your corporate platform.

And separately: Qwen-Image-Edit already looks like a more suitable foundation for your task than Kandinsky, because your task is precisely editing existing photos through natural language, not generating a picture from scratch.
