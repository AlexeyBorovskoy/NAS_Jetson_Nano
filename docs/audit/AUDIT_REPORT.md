# Полный технический аудит NAS_Jetson_Nano / Full technical audit

**Дата / Date:** 2026-08-30. **Режим / Mode:** READ-ONLY / NON-DESTRUCTIVE (по промту `jetson_project_full_audit_prompt.md`). **Метод / Method:** 3 параллельных read-only проверки живой системы (SSH `admin@192.168.0.50`, без sudo, без чтения секретов) + синтез. Полные данные — в отдельных файлах этой папки, здесь — сводный отчёт по структуре §42.1 промта.

## 1. Executive Summary

🇷🇺 Проект работоспособен и стабилен: 13 контейнеров, ноль рестартов, температуры и нагрузка в норме, бэкапы БД дважды проверены реальным восстановлением. Главный неустранённый риск — единственная копия семейных фото (Immich, ~6-9 ГБ) без offsite-бэкапа. Второй по значимости — расхождение между git (переименованный layout) и живым устройством (старый деплой), частично устранённое в ходе этого же аудита. Критических (CRITICAL) находок безопасности нет; периметр (правила №2/4/13 CLAUDE.md) соблюдён.

🇬🇧 The project is operational and stable: 13 containers, zero restarts, temperatures and load within range, database backups verified twice by real restore. The main unresolved risk is the single copy of family photos (Immich, ~6-9 GB) without an offsite backup. The second is the divergence between git (renamed layout) and the live device (old deployment), partially closed during this same audit. No CRITICAL security findings; the perimeter (CLAUDE.md rules #2/4/13) is respected.

## 2. Scope / Область

Windows-репозиторий `NAS_Jetson_Nano` (источник кода/конфигурации) + живое устройство `192.168.0.50` (источник факта работы) + ограниченная read-only проверка VPS (nginx/AmneziaVPN/coturn — только чтение, без изменений). Vostro (offsite-узел) — недоступен в момент аудита (вне корпоративной LAN), не проверен независимо.

## 19. Reliability

Реальный прецедент отказа — аппаратный сброс 2026-08-17, причина не установлена (задокументировано ранее, не переисследовалось).

## 20. Performance

`RUNTIME.md` §6. Throttling не обнаружен, GPU простаивает (0%), CPU/RAM с умеренной нагрузкой, температуры с большим запасом. Power mode — MAXN.

## 21. Monitoring

Netdata + Uptime Kuma (5 HTTP-мониторов) + Portainer + Beszel Agent→Hub. Покрытие неполное (Samba/БД/Redis не отдельными Kuma-мониторами), но системный уровень закрыт Netdata — принятый компромисс.

## 22. Backup

БД — ежедневно, локально + offsite (Vostro, Фаза 1, restic). Фото Immich — **не бэкапятся offsite**, единая точка отказа. Восстановление проверено дважды (09.08, 24.08).

**Можно ли восстановить Jetson с нуля только по имеющимся данным: PARTIALLY.** БД — да (дважды подтверждено). Фото — нет (единственная копия). `.env`/секреты — только на устройстве, без redacted-снапшота.

## 23. Reproducibility

**Оценка: C — существенные неизвестные.** См. `DEPENDENCIES.md` §6. Главные причины: реальные значения `.env` нигде не задокументированы воспроизводимо; деплой устройства системно отличается от git; один сервис (`nasa-api`) без пиннинга зависимостей.

## 24. Code Quality

Выборочно (не построчно весь репозиторий): модульность приемлемая (роутеры разделены по доменам), dead code не обнаружен при чтении, error handling единообразный, но местами широкий `except Exception`. Сильная сторона — комментарии объясняют «почему», не «что» (пример: `talk_bot.py` про OCS form-vs-JSON баг).

## 25. Tests

17 файлов в `tests/`, преимущественно shell smoke-тесты (сеть/сервисы/хранилище). Единственный unit-тест — `test_talk_alert_selftest.py`, написан как прямая регрессия конкретного пойманного дефекта. **Test coverage maturity: 1 — единичные тесты.** Зоны с историей продакшн-багов (auth, PII-редактирование, OCS-парсинг, restart whitelist) не покрыты тестами, кроме одной.

## 48. Финальное заключение / Final conclusions

1. **Работоспособен ли проект сейчас?** Да — 13/13 контейнеров healthy/up, ноль рестартов.
2. **Можно ли безопасно продолжать разработку на текущей базе?** Да, с оговоркой — сначала закрыть TD-01 (git↔устройство) и TD-02 (offsite фото).
3. **Насколько воспроизводима существующая установка?** C — существенные неизвестные (реальные `.env`, деплой устройства).
4. **Есть ли риск потерять рабочую конфигурацию?** Да, для фото Immich — реальный и неустранённый (R-01).
5. **Какие компоненты наиболее критичны?** AmneziaVPN на VPS (правило №2), `nasa-tunnel`, БД Nextcloud/Immich, `.env`.
6. **Какие компоненты наиболее устаревшие?** Ubuntu 18.04.6, Python 3.6.9 (системные, EOL), `docker-compose.stage1.yml`.
7. **Какой главный технический долг?** TD-02 (фото без offsite) и TD-01 (git↔устройство, частично закрыт сегодня).
8. **Какой главный security-риск?** CORS `*` на API + EOL база ОС без подтверждённого ESM — оба MEDIUM, ничего CRITICAL.
9. **Какой главный эксплуатационный риск?** Единая точка отказа для фото (SSD) без offsite-копии.
10. **Где главный bottleneck?** RAM Jetson (4 ГБ, уже 51-54% в простое) — не CPU, не GPU, не сеть.
11. **Насколько хватает текущего Jetson?** Хватает для текущего набора сервисов с запасом по CPU/температуре, но не для добавления ML-инференса без вытеснения существующего.
12. **Какие задачи ему уже нецелесообразно давать?** Локальный CV/AI-инференс — GPU технически готов, но конкурирует за RAM с Immich/Nextcloud/Postgres.
13. **Что можно модернизировать без изменения архитектуры?** Пиннинг зависимостей, logrotate, явная проверка места в preflight, developerи README↔CLAUDE.md синхронизация.
14. **Что требует рефакторинга?** Ничего критического — точечные правки (CORS, JWT-секрет), не структурный рефакторинг.
15. **Что требует отдельного сервера?** Тяжёлый ML/LLM-инференс (уже частично так — Ollama на Vostro).
16. **Что потребует нового оборудования?** Любое серьёзное развитие CV/AI-направления — JetPack 4.6.1 не обновляется дальше на Nano.
17. **Какие 5 изменений дадут максимальный эффект?** (1) Фаза 2 offsite-бэкапа фото, (2) завершить Часть B миграции устройства, (3) закрепить версии зависимостей/образов, (4) явная проверка места в preflight, (5) синхронизировать README с CLAUDE.md.
18. **В каком порядке разумно модернизировать?** P0 (offsite фото) → P1 (миграция устройства, EOL-решение по ОС) → P2 (безопасность API, тесты, SD-мониторинг, coturn) → P3 (косметика: dangling images, `.bak` ротация, `stage1.yml`).
