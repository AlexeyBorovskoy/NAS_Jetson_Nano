```text

│   └── writing/
│       ├── HABR_ARTICLE_SOURCE_INDEX.md
```

`_local/` должен оставаться вне Git.

В публичный GitHub рекомендуется помещать:

- собственные измерения и итоговые агрегированные таблицы;

Не рекомендуется помещать в публичный GitHub:

- полные копии чужих статей;

- большие исходные графики/логи;
- материалы, лицензия которых не разрешает распространение.

# 11. КАНДИДАТЫ НА ОСНОВНОЙ СЮЖЕТ

Агент должен выбрать только после завершения работ и на основании фактов.

### Вариант A — «Я перестал доверять своему NAS»

Сюжет:

```text
всё работает
→ полный аудит
→ обнаруживаются скрытые failures
→ система оказывается менее устойчивой, чем казалось
→ quality/security/recovery pipeline
→ доказательство устойчивости
```

### Вариант B — «Старый Jetson вместо нового сервера»

Сюжет:

```text
можно купить новое железо
→ измеряем реальный bottleneck
→ оказывается, проблема не в CPU
→ оптимизируем software/operations
→ получаем измеримый результат
```

### Вариант C — «NAS, который умеет объяснить, что у него сломалось»

Сюжет:

```text
обычный NAS
→ monitoring
→ deterministic diagnostics
→ incident classification
→ AI explanation
→ безопасный self-healing
```

Третий вариант потенциально имеет самый выраженный wow-эффект, но только если функция реально будет реализована и измерена.


# 17. AI POLICY ДЛЯ СТАТЬИ

AI разрешено:

- искать источники;
- строить outline;
- проверять логические разрывы;
- искать повторения;
- проверять терминологию;
- редактировать предложения;
- предлагать варианты заголовка;
- проверять факты по источникам;
- анализировать комментарии к первой статье;
- проверять текст по quality gate.

AI не должен:

- придумывать личный опыт;
- придумывать аварии;
- придумывать метрики;
- придумывать мотивы автора;
- делать фальшивый «человеческий» юмор;
- генерировать всю статью одним проходом;
- заменять инженерные доказательства красивой прозой.

# 19. ПРЕДВАРИТЕЛЬНАЯ РАБОЧАЯ ФОРМУЛА ЗАГОЛОВКА

Не использовать clickbait, который статья не оправдывает.

Сильная структура:

```text
[конкретное ограничение/старое железо]
+
[конкретная проблема]
+
[существенное изменение]
```

Примеры только как направление, НЕ как готовые заголовки:

- «Что ещё можно выжать из Jetson Nano с 4 ГБ: аудит, восстановление и год эксплуатации домашнего NAS»
- «Я думал, что мой NAS надёжен. Аудит показал обратное»
- «Старый Jetson Nano вместо нового сервера: что реально ограничивало мой домашний NAS»
- «NAS на Jetson Nano после года эксплуатации: что сломалось, что пришлось переписать и что оказалось лишним»
- «Домашний NAS, который сам объясняет свои аварии: от мониторинга к безопасной диагностике»

Выбор делается только после завершения проекта.

# 20. ЛИЦЕНЗИОННОЕ ПРАВИЛО

Если материал:
- CC BY / CC BY-SA — допустимо хранить и использовать по условиям лицензии;
- бесплатный, но copyright — можно читать/хранить для личного использования, но не считать автоматически разрешённым для публикации в GitHub;
- коммерческий — хранить только локально после законной покупки;
- web article — предпочтительно хранить ссылку и собственный конспект.

Не использовать пиратские библиотеки.
