## 3. Три дефекта, найденные и устранённые 2026-08-22

Повод: в Telegram-отчёт приходили три ❌ по внешнему доступу, и не работала
синхронизация на телефонах.

### 3.1. 🔴 Nextcloud навязывал всем клиентам мёртвый адрес

**Симптом.** Телефоны не синхронизируются.

**Замер.** Запрос с любого адреса — из дома и снаружи — получал один ответ:

```
GET http://192.168.0.50:8080/     →  302  Location: https://193.8.215.130:8443/login
POST /index.php/login/v2          →  {"login":"https://193.8.215.130:8443/login/v2/flow/…"}
```

То есть телефон, стоящий в двух метрах от NAS, отправлялся на адрес VPS.

**Причина.** В конфигурации остались значения от старого адреса VPS:

```
overwritehost      = 193.8.215.130:8443
overwriteprotocol  = https
overwrite.cli.url  = https://193.8.215.130:8443
```

Адрес VPS сменился 2026-08-09 (`193.8.215.130` → `95.163.176.103`), но эти три ключа
не поправили. Важная поправка владельца, подтверждённая замером: **старый адрес не
«мёртв» — VPS держит оба**, `193.8.215.130/32` и `95.163.176.103/32` на `enp0s3`.
Он недостижим по пути: заблокирован российскими ISP, а сервисные порты и без того
закрыты для не-VPN источников. Для клиента под VPN рабочий адрес — внутренний
`172.29.172.1`, потому что публичные IP исключены из туннеля по определению
(иначе VPN зациклится). Замер с рабочей станции под VPN:

```
https://193.8.215.130:8443/status.php → соединение закрыто
https://95.163.176.103:8443/status.php → таймаут
http://172.29.172.1:8080/status.php    → HTTP 200
```

**Исправление — не «поменять адрес на новый», а перестать навязывать адрес вообще:**

```bash
occ config:system:delete overwritehost
occ config:system:delete overwriteprotocol
occ config:system:set overwrite.cli.url --value=http://172.29.172.1:8080
occ config:system:set trusted_domains 4 --value=95.163.176.103
occ config:system:set trusted_domains 5 --value=borovskoy.dynv6.net
occ config:system:set trusted_domains 6 --value=172.29.172.1
```

Теперь каждый клиент остаётся на том адресе, по которому пришёл. Схема выдерживает
следующую смену IP: чинить будет нечего.

**Проверено после:**

```
дома:      GET /  →  302 Location: http://192.168.0.50:8080/login          ✅
под VPN:   login/v2 → "endpoint":"http://172.29.172.1:8080/login/v2/poll"  ✅
чужой Host: evil.example.com → страница «недоверенный домен»               ✅ защита вернулась
```

**Побочный эффект, который стоит назвать:** пока стоял `overwritehost`, проверка
доверенного домена была фактически выключена. Сняв навязывание, мы её включили обратно —
это плюс к безопасности, но именно поэтому пришлось перечислить все реальные адреса.

**Откат:** три `occ config:system:set` с прежними значениями (выписаны выше).

### 3.2. 🟠 nginx на VPS терял порт в адресе

**Замер.** Сразу после 3.1 VPN-клиент получал `Location: http://172.29.172.1/login` —
**без `:8080`**, то есть на порт 80, где ничего не слушает и куда ufw не пускает.

**Причина.** В HTTP-блоке `nextcloud.conf` стояло `proxy_set_header Host $host` —
`$host` отбрасывает порт. В HTTPS-блоке был правильный `$http_host`.

**Исправление** на VPS, `/opt/nasa/nginx/conf.d/nextcloud.conf`: `$host` → `$http_host`,
затем `nginx -t` и `nginx -s reload` (без пересоздания контейнера).

**Проверено:** `"endpoint":"http://172.29.172.1:8080/login/v2/poll"` — порт на месте. ✅

**Откат:** `/opt/nasa/nginx/conf.d/nextcloud.conf.bak.20260822`.

### 3.3. 🔴 Talk-бот 12 дней бил в стену — 16 300 отказов в сутки

Найдено не по жалобе, а **по замеру нагрузки**: `load average 5.6`, Nextcloud ест
**213 % CPU**, шесть воркеров apache заняты. Стали смотреть, кто его нагружает.

**Замер.** 796 из 800 последних запросов к Nextcloud — наш собственный Talk-бот
(`python-httpx`, пользователь `admin`, из контейнера `homecloud_nasa_api`), опрос шести
комнат, и на **каждый** запрос — HTTP 400 с HTML-страницей на 22 КБ вместо OCS-JSON.

```
{"error": "Trusted domain error.", "code": 15}
```

Бот ходит по имени `host.docker.internal`, которого не было в списке доверенных доменов.

**Давность.** По журналу: 09.08 — 611 запросов, 10.08 — 7 247, дальше ровно ~16 300
в сутки **каждый день до сегодня**. То есть отказ идёт **с выкатки Фазы C (2026-08-10)**,
двенадцать суток, порядка 200 000 неудачных запросов. Семейный ИИ-помощник не читал
комнаты ни одного дня из тех, что считался работающим.

**Исправление:**

```bash
occ config:system:set trusted_domains 7 --value=host.docker.internal
```

**Проверено после:**

| Что | До | После |
|---|---|---|
| Ответ на опрос | `400 Bad Request` | `304 Not Modified` — штатный long-poll ✅ |
| Запросов к Nextcloud за минуту | шторм | 6 |
| CPU `homecloud_nextcloud` | **213 %** | **9.9 %** |
| load average | 5.89 | 4.01 и падает |

Это прямо закрывает часть замечания tklim про «4 ГБ мало»: **заметная доля нагрузки
на Nano была самодельной**, а не следствием нехватки железа.

### 3.4. 🟠 Отчёт в Telegram кричал волком

**Симптом.** Три ❌ по внешнему доступу и «Beszel Hub unreachable».

**Причина двойная:**

1. В `/etc/nasa-monitor/nasa-monitor.env` от 23 июня осталось `SERVER_IP="193.8.215.130"`.
   По этому же адресу ходил и Beszel-запрос — отсюда его «unreachable».
2. **Проверка была бессмысленна по построению.** Она curl-ила сервисные порты VPS
   с публичного выхода Jetson — а Фаза 1 закрыла их для всех, кроме VPN. То есть
   ❌ был бы и с правильным адресом, всегда.

**Исправление.** Адрес поправлен, а сама проверка переписана:

- цепочка `клиент → nginx → обратный туннель → Jetson` меряется **на самом VPS**
  против `127.0.0.1` — это тот же путь, которым идёт запрос VPN-клиента;
- взяты настоящие health-эндпоинты: `/status.php`, `/api/server/ping`, `/health`,
  `/healthcheck` (прежняя проверка дёргала `/`, который у шлюза и API отдаёт 404);
- наружная проверка **инвертирована**: теперь тревога — это порт, который **ответил**
  из интернета. Закрытый порт — ✅, как и должно быть по правилу №4.

**Проверено:** отчёт печатает пять ✅ через туннель, `ports closed to the internet —
rule #4 holds`, и Beszel снова видит оба агента.

**Откат:** `/usr/local/sbin/nasa-daily-report.sh.bak.20260822`,
`/etc/nasa-monitor/nasa-monitor.env.bak.20260822`.

## 7. Грабли, добавленные этим днём

1. **Отчёт, который каждый день показывает ❌ на штатное состояние, — сломанный отчёт.**
   Три креста по внешнему доступу были нормой с Фазы 1 и приучили их не читать.
   Проверять надо то, от чего зависит человек, а тревожиться — на нарушение правила,
   а не на его соблюдение.
2. **Смена IP ломает не один файл, а список файлов.** После 09.08 старый адрес остался
   в `overwritehost`, `overwrite.cli.url`, `trusted_proxies`, `nasa-monitor.env` и в
   десятке install-скриптов. Правильный вывод не «поправить адрес», а **перестать
   хранить адрес там, где можно не хранить**.
3. **`$host` в nginx отбрасывает порт, `$http_host` — нет.** На нестандартном порту
   это ломает любой сгенерированный редирект.
4. **Nextcloud отвечает на недоверенный домен кодом 400 и HTML-страницей.** Клиент,
   ожидающий JSON, видит «Bad Request» и не сообщает настоящей причины — она в теле.
5. **Нагрузка — это тоже симптом.** Дефект, который не жаловался никому, нашёлся
   по `load average`. Жалоба владельца была про телефоны, а самый дорогой дефект
   был рядом и молчал.
